# XP 极限编程案例：与原型差别、问题清单、与传统结合

## 题干（原题抄写）

> 阅读以下关于软件架构设计的叙述，回答问题1至问题3。某公司要在现场开发一个网站应用系统，特点：规模不大；工期短；用户需求不明确；没有大的技术风险；一些模块可外包给其他公司。王工提出采用 XP（极限编程），理由是简洁、减轻开发人员负担、快速适应市场、缩短投资回收期；李工认为 XP 存在问题，建议原型开发。最终项目组决定采用 XP，并针对李工提出的问题采取措施。
>
> 【问题1】（8分）小规模发布（small release）是 XP 的基本元素之一。① 原型系统和 XP 小规模发布的系统的主要差别？② 为什么该项目组没有采用原型开发方法？
> 【问题2】（8分）简要说明采用 XP 方法可能会存在哪些问题。
> 【问题3】（9分）李工提出项目规模扩大后 XP 不再适用，王工赞同但提出可将 XP 与传统软件开发过程相结合。简要说明如何结合。
>
> （来源：软考达人题库章节练习 题目171，章节标记“第五章 软件工程基础知识（新第2版）/第一节 软件工程”；案例简答题，页面标注暂不支持作答；本地未找到该案例原题）

## 考场答案与采分要点

**问题1①（功能真实性对立）**：原型是一次性验证工具（让用户确认需求或测试关键技术），展示的功能不是实际系统功能，不能评价实际系统；XP 小规模发布是真实产品子集——开始时功能不全，但每个已含功能与可发布产品定义一致：完整性上是一组实用功能集，质量上可健壮运行。
> ⚠️ 题库官方答案“**考试时**不包括足够的功能”系 OCR 错字，应为“**开始时**”。

**问题1②（三条线索映射）**：无技术风险 → 不需原型验证关键技术；工期短 → 原型与真实开发工作量相当，直接开发更省时；需求不明确/多变 → 用 XP 的代码重构、持续集成、小规模发布应对。

**问题2（六类问题）**：①开发团队、管理层、客户不理解 → 阻碍实施；②忽视文档，以 XP 为借口拒写必要文档；③XP 针对单一团队设计，外包方参与难组织；④缺乏客户参与 → 用户故事编写、优先级确认困难；⑤项目规模扩大后不适用；⑥对客户、开发人员、管理者素质要求高。

**问题3（与传统结合）**：与**增量式开发**结合——将大规模项目划分为若干有共同目标的小规模项目，用 XP 组织小项目开发、用传统软件过程监控全局，在此基础上建立面向目标的项目管理。

**采分点核对**：问题1 = 功能真实性对立 + 三条线索映射（无风险/工期短/需求变）；问题2 = 六类框架“人、文、团队、客户、规模”；问题3 = 增量式、大拆小、XP 管内/传统管外、面向目标。
