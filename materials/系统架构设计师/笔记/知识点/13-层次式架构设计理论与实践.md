# 第 13 章 层次式架构设计理论与实践

> 目录骨架依据《系统架构设计师教程（第 2 版）》；按专题汇集概念、例题与辨析。

## 13.1 层次式体系结构概述

### 13.1.1 层次式架构核心定义与设计原理
1. **层次式架构概念**：
   - 层次式体系结构（Layered Architecture）将系统组织为多层构件，每一层为上层提供服务，并作为下层的客户。
   - **严格分层（Strict Layering）**：某一层的构件只能调用其紧邻的直接下层构件提供的服务。
   - **松散分层（Relaxed Layering）**：某一层的构件可以跨层调用更低层构件提供的服务（如表现层直接调用数据访问层），提高运行性能，但牺牲了隔离性。
2. **层次式架构的优势与代价**：
   - **核心优势**：
     - **关注点分离（Separation of Concerns）**与**高内聚低耦合**；
     - **支持软件复用**：只要接口保持稳定，某一层可被其他系统复用；
     - **便于团队协作与并行开发**：各层按明确接口划分任务；
     - **易于替换与技术迁移**：如更换底层数据库或前端 UI 框架时不影响业务逻辑层。
   - **主要代价与局限**：
     - **性能开销**：请求穿透多层导致额外的函数调用与数据封装转换开销；
     - **级联修改风险**：顶层新增需求可能导致自顶向下所有层级接口均需联动调整；
     - **过度设计风险**：在简单 CRUD 系统中引入多层容易造成代码冗余。

## 13.2 表现层框架设计

### 13.2.1 表现层设计模式

#### 1. MVC 架构模式：三组件职责与归类判别 ⭐⭐
[考查：综合知识 / 案例分析（元素归类填表）]

- **模型（Model）**：封装与业务逻辑相关的**数据及对数据的处理方法**；可直接访问数据库；**不依赖 View 和 Controller**（不关心如何显示、如何被操作）；数据变化通过刷新机制公布，View 须事先在 Model 上注册才能感知改变。
- **视图（View）**：实现数据**有目的的显示**；View 中**一般没有程序上的逻辑**；为实现刷新需访问所监视的 Model。
- **控制器（Controller）**：起**不同层面间的组织作用**，控制应用程序流程；**处理事件并作出响应**——"事件"包括用户行为和 Model 上的改变。
- **归类判别口诀**：**名词 → Model（数据/工件/角色），纯展示 → View（图/报表），动词 → Controller（操作/动作）；活动、事件类条目三类不归**（典型干扰项）。
- **应用实例**（Scrum 项目管理系统案例）：Model = Project、Product Backlog、用户故事、用户、Task、Sprint、产品负责人、Sprint Backlog；View = Sprint 燃尽图、Release 燃尽图；Controller = 新建项目、估算任务预计完成时间；干扰项 = Sprint 回顾会议、交付产品增量（活动/事件）。
- **易错点**："用户 / 产品负责人"是角色**数据**归 Model，不因为是"人"就归 Controller。

#### 2. MVC vs MVP vs MVVM 表现层演进对比
| 模式名称 | 核心交互逻辑 | 视图与模型解耦度 | 驱动机制与核心特征 |
|---|---|---|---|
| **MVC** | Controller 处理输入，更新 Model，View 监听 Model 变化更新展示 | 弱解耦（View 与 Model 存在直接关联） | 经典服务端 Web 框架（Struts2, Spring MVC） |
| **MVP** | Presenter 作为核心枢纽，View 与 Model 完全隔离 | 强解耦（View 与 Model 零依赖，通过接口交互） | 早期桌面客户端与 Android 开发，Presenter 容易膨胀 |
| **MVVM** | ViewModel 绑定 Model，通过**双向数据绑定（Data Binding）**自动同步 View | 极强解耦（无须手动编写视图刷新代码） | 现代前端主流（Vue, React, WPF），数据驱动视图 |

### 13.2.2 使用 XML 设计表现层，统一 Web Form 与 Windows Form 的外观
- 利用 XML 定义与平台无关的界面元数据（布局、控件类型、样式属性）；
- 结合 XSLT 转换引擎或特定解析器，将统一的 XML 界面描述分别渲染为 B/S 架构下的 Web 页面或 C/S 架构下的桌面窗体，实现“一次界面设计，多端统一呈现”。

### 13.2.3 表现层中 UIP 设计思想
- **UIP（User Interface Process，用户界面过程）**：
  - 微软模式与实践指南提出的经典设计思想，将**用户界面导航与业务工作流解耦**。
  - UIP 专门管理多页面/多步骤交互之间的状态跳转逻辑（如向导流程 Wizard、电商结算结算流 Checkout Process）。
  - **核心价值**：页面视图（View）只负责展示当前步骤，无需知道上一步或下一步跳向何处，业务逻辑组件也不必感知页面流转状态，极大提升了界面流程的复用性与可配置性。

### 13.2.4 表现层动态生成设计思想
- 通过运行时元数据驱动（数据库配置、JSON/XML 模式定义），动态组装表单与视图控件，支持低代码（Low-Code）与高度定制化 SaaS 应用。

## 13.3 中间层架构设计

### 13.3.1 业务逻辑层组件设计
1. **业务逻辑层（BLL）定位与核心职责**：
   - 处于表现层与数据访问层之间，是系统的核心中枢，负责实现全部企业业务规则、数据验证、业务计算与流程控制。
2. **经典设计模式在业务逻辑层的应用**：
   - **门面模式（Facade）**：为子系统中的一组接口提供一个统一高层接口，降低表现层与内部多业务组件之间的耦合度。
   - **领域模型设计（Domain Model）**：
     - **贫血模型（Anemic Domain Model）**：领域对象仅包含属性与 getter/setter（POJO），所有业务逻辑全部放在 Service 服务类中（简单直观，但 Service 容易臃肿）。
     - **充血模型（Rich Domain Model）**：领域实体既包含数据状态，也封装其内在的业务行为与领域规则，符合面向对象设计思想。

### 13.3.2 业务逻辑层工作流设计
1. **工作流（Workflow）基本概念**：
   - 工作流是业务流程的计算机化表示与自动化执行，将业务逻辑中的“流程流转控制”与“具体业务逻辑实现”解耦。
2. **工作流参考模型（WfMC）核心构件**：
   - **工作流机（Workflow Engine）**：解释流程定义、控制活动流转与状态迁移的核心服务。
   - **过程定义（Process Definition）**：由活动（Activity）、变迁（Transition）、路由条件（Condition）构成的有向图。
   - **工作流客户端（Workflow Client）**：供人工任务认领与审批交互的界面。
   - **调用应用程序（Invoked Applications）**：流程执行过程中自动触发调用的后台服务。

### 13.3.3 业务逻辑层实体设计
- **DTO（Data Transfer Object，数据传输对象）**：纯数据载体，跨层传输，避免领域实体直接暴露给表现层，减少远程网络调用开销。
- **VO（View Object / Value Object）**：表现层视图对象，专门匹配 UI 展示需要；或领域驱动设计中的“不可变值对象”。
- **PO / Entity（持久化对象 / 领域实体）**：与数据库表结构映射或承载核心业务标识的领域实体。

### 13.3.4 业务逻辑层框架
- **Spring 框架**：基于 **IoC（控制反转 / 依赖注入）** 实现组件解耦，基于 **AOP（面向切面编程）** 实现声明式事务、日志审计与安全控制。
- **轻量级 vs 重量级对比**：EJB（Enterprise JavaBeans）过去依赖沉重容器与 RMI，现代企业系统普遍全面转向 Spring / Spring Boot 等轻量级业务框架。

## 13.4 数据访问层设计

### 13.4.1 5 种常用数据访问模式
1. **在线访问模式（Online Access）**：应用直接连接数据库执行 SQL，适用于单机或小规模轻量应用。
2. **DAO 模式（Data Access Object，数据访问对象）**：将数据访问逻辑完全抽象并封装在独立的 DAO 接口中，业务层仅依赖 DAO 接口，彻底屏蔽底层持久化细节。
3. **ORM 模式（Object-Relational Mapping，对象关系映射）**：通过元数据映射将面向对象实体与关系数据库二维表绑定。
4. **表格数据入口模式（Table Data Gateway）**：充当数据库表的网关对象，一个实例处理表中所有行的数据操作。
5. **行数据入口模式（Row Data Gateway / Active Record）**：充当数据表中单条记录的网关对象，对象实例对应单行数据，同时内嵌持久化保存方法。

### 13.4.2 工厂模式在数据访问层应用
- **抽象工厂模式（Abstract Factory）**：定义创建数据访问接口族的规范（如 `IUserDao`, `IOrderDao`），具体工厂按数据库类型实现（如 `SqlserverFactory`, `OracleFactory`, `MySqlFactory`）。
- **结合反射（Reflection）与配置文件**：在运行时动态加载具体工厂类，实现零代码改动即可无缝切换底层数据库。

### 13.4.3 ORM、Hibernate 与 CMP2.0 设计思想

[考查：综合知识（定义分类、手写 SQL 辨析）/ 案例分析 / 论文素材]

#### 持久层 ORM 框架选型：全自动 ORM vs 半自动 ORM（MyBatis vs Hibernate / EF） ⭐⭐⭐

- **ORM 核心概念**：对象-关系映射（Object-Relational Mapping），解决面向对象模型与关系型数据库二维表之间的阻抗不匹配（Impedance Mismatch）。
- **全自动 ORM vs 半自动 ORM 对比模型**：

| 特性维度 | 全自动 ORM（Hibernate / JPA / Entity Framework / JDO） | 半自动 ORM（MyBatis / 原 iBatis） |
|---|---|---|
| **核心驱动思想** | **以对象为中心（Object-Centric）** | **以 SQL 为中心（SQL-Centric / SQL Mapper）** |
| **SQL 生成机制** | 框架引擎根据对象映射关系**全自动动态生成**，屏蔽底层 SQL | **必须由程序员手工编写原生 SQL**（XML 或注解维护） |
| **查询抽象语言** | HQL（Hibernate Query Language）、LINQ（.NET EF） | 原生 SQL（支持特定数据库专属函数与语法特性） |
| **数据库独立性** | **高**（框架通过各数据库 Dialect 方言屏蔽语法差异） | **较低**（SQL 绑定具体方言，跨库迁移需改写 SQL） |
| **执行计划控制力** | **弱**（黑盒生成，深层多表关联难以精细优化，易产生 N+1 查询） | **极强**（手写 SQL，可精确控制执行计划、索引 Hint 与覆盖索引） |
| **DBA 审计友好度** | **差**（动态生成难以静态分析与审查） | **极高**（SQL 集中写在 XML 文件中，DBA 可独立走查与压测） |
| **典型适用场景** | 内部企业管理系统（ERP/OA）、中小型项目、强调面向对象与快速 CRUD 开发 | 大型互联网平台、高并发电商交易、复杂报表多表联查、强性能调优诉求系统 |

- **口诀速记**：**“全自动操作实体树，Hiber、EF 与 JDO；唯有 MyBatis 半自动，Mapper 手写 SQL 留。”**
- **高频设陷点**：
  - ❌ 误将 Entity Framework 当做需要手写 SQL 的框架 $\rightarrow$ EF 是微软 .NET 的官方旗舰全自动 ORM（等价于 Java 界的 Hibernate），LINQ 操作对象，SQL 全自动生成。
  - ❌ 误以为 MyBatis 只能简单映射 $\rightarrow$ MyBatis 优势在于 SQL 与代码解耦（集中管理），对底层控制度最高。
  - 2015 年下半年系统架构设计师下午案例题二（数据访问层 Hibernate vs iBatis 选型对比）。
  - 2016 年下半年系统架构设计师论文题（《论从 Hibernate 到 MyBatis 的 ORM 架构演进》）。
  - 题库章节练习 （需要程序员手写 SQL 的是 MyBatis

### 13.4.4 灵活运用 XML Schema
- **XML Schema 的作用**：定义 XML 实例文档的合法构建模块，提供丰富的数据类型支持、命名空间隔离与复杂的业务完整性约束验证，广泛用于异构企业系统间的数据交换与消息契约。

### 13.4.5 事务处理设计
1. **ACID 核心特性与隔离级别**：
   - **原子性（Atomicity）**、**一致性（Consistency）**、**隔离性（Isolation）**、**持久性（Durability）**。
   - **SQL-92 四大隔离级别**：读未提交（Read Uncommitted，脏读）、读已提交（Read Committed，不可重复读）、可重复读（Repeatable Read，幻读）、串行化（Serializable）。
2. **分布式事务解决方案选型矩阵**：
   - **强一致性方案**：
     - **两阶段提交（2PC）**：准备阶段（Prepare）+ 提交阶段（Commit），依赖 XA 规范；存在同步阻塞、单点故障（协调者）与脑裂数据不一致问题。
     - **三阶段提交（3PC）**：引入超时机制与预提交阶段（CanCommit $\to$ PreCommit $\to$ DoCommit），改善阻塞但增加了网络交互轮次。
   - **最终一致性（BASE 理论）方案**：
     - **TCC 补偿模式**：Try（资源检查与预留） $\to$ Confirm（确认执行业务） / Cancel（取消与补偿回滚），业务侵入性强但性能好。
     - **Saga 状态机模式**：长事务拆分为一系列本地短事务，正向执行失败时触发逆向补偿事务。
     - **基于可靠消息的最终一致性**：结合消息队列（如 RocketMQ 事务消息 / 本地消息表），通过重试与死信队列保障最终状态一致。

### 13.4.6 连接对象管理设计（数据库连接池）
1. **连接池核心工作机制**：
   - 建立数据库物理连接涉及 TCP 三次握手、认证与资源分配，开销极其高昂。连接池在应用启动时预先创建并缓存一组物理连接，按需借出、用毕归还复用。
2. **关键性能与健康调优参数**：
   - `initialSize`：连接池启动时初始化的物理连接数；
   - `maxActive / maximumPoolSize`：最大并发连接上限（过大易导致数据库内存溢出与上下文切换剧烈，过小导致应用排队等待超时）；
   - `maxWait / connectionTimeout`：获取连接的最大等待超时时长；
   - `minIdle / minimumIdle`：最小空闲保持连接数；
   - **连接保活与泄漏检测**：通过 `testOnBorrow` 或后台空闲连接检测线程（Heartbeat SQL），剔除因数据库断开或网络超时导致的失效连接；通过连接租期检测追踪未正常 close 的连接泄漏。

## 13.5 数据架构规划与设计

### 集中式与分布式数据架构：CRSS 高可用、读写缓存与扩展

[考查：案例分析（数据架构选型、容错与扩展）]

- **集中式数据架构**：处理能力、数据存储和管理集中在一个中心站点，客户端可本地或远程访问。结构和管理较简单，开发运行成本低；容量受中心资源限制，中心数据库也可能成为性能瓶颈和单点故障。扩容主要采用纵向扩展（Scale Up），如增加 CPU、内存、磁盘或升级主机。
- **分布式数据架构**：多个相互连接的计算机和局部数据库位于一个或多个站点，应用可访问不同节点的数据。复制、分片、缓存和全文检索等可扩展容量、吞吐或可用性；同时增加跨节点协调、复制一致性和运维复杂度。扩展主要采用横向扩展（Scale Out），通过增加节点及调整数据分布提升能力。
- **读写分离与缓存**：局部主库处理持久化写入，热备副本用于故障切换，缓存节点承担热点读取。读请求先查缓存，未命中时读取数据库并回填；新增通常写主库，修改和删除数据库记录后失效对应缓存。数据库副本与缓存均应避免单节点部署。
- **工程边界**：读写分离主要扩展读能力，主库仍承担写入；缓存失效和副本延迟会影响读取新鲜度。故障切换、读后写一致性和跨节点数据同步需按业务要求设计。

| 架构 | 扩展方法 | 主要手段 | 主要代价 |
|---|---|---|---|
| 集中式 | 纵向扩展（Scale Up） | 扩充 CPU、内存、磁盘或升级主机 | 单节点容量上限与故障影响集中 |
| 分布式 | 横向扩展（Scale Out） | 数据复制、水平/垂直分片、缓存、全文搜索、增加节点 | 一致性、协调和维护复杂度上升 |

### 13.5.1 数据库设计与类的设计融合
1. **阻抗不匹配（Impedance Mismatch）本质**：
   - 面向对象世界强调封装、继承、多态与对象图导航；关系数据库世界强调集合代数、二维关系表、主外键参照与规范化范式。
2. **面向对象继承关系的 3 种关系表映射策略**：
   - **单表继承（Single Table Inheritance / Table per Hierarchy）**：
     - 将整棵类的继承体系全部映射到**同一张数据库表**中，表中包含所有子类的全部属性字段，并额外增加一个“鉴别器（Discriminator）”列标识具体子类类型。
     - *优点*：查询多态实体无需联表（JOIN），性能最高；*缺点*：稀疏列严重，非共有字段无法设置 NOT NULL 完整性约束。
   - **类表继承（Class Table Inheritance / Table per Type）**：
     - 每个类（包括抽象父类）映射为独立的数据库表，子类表通过主键作为外键引用父类表的主键。
     - *优点*：表结构规范，无冗余空值；*缺点*：多态查询必须执行深度 JOIN 操作，性能损耗较大。
   - **具体类表继承（Concrete Table Inheritance / Table per Concrete Class）**：
     - 仅为具体子类创建表，每张子类表中包含从父类继承的所有字段及子类特有字段。
     - *优点*：单实体查询单表解决；*缺点*：父类属性修改需改动所有子类表，跨子类多态查询需 UNION。

### 13.5.2 数据库设计与 XML 设计融合
- 将半结构化数据以 XML / JSON 字段类型存储于关系数据库中（如 PostgreSQL / MySQL JSONB 类型），兼顾强结构化核心事务与高扩展性弹性业务元数据。

## 13.6 物联网层次架构设计

### 13.6.1 物联网经典三层体系结构
1. **感知层（Perception Layer）**：
   - 负责物理世界信息的采集与识别。核心技术包括 **RFID 电子标签**、传感器网络（WSN）、二维码/条形码、摄像头、GPS 及工业执行器。
   - **RFID vs 条形码高频辨析**：RFID 支持非接触远距离群读、穿透性强、可反复擦写数据、存储容量大、抗恶劣环境能力高；条形码成本极低但需近距离光学视线对准、只读且容量小。
2. **网络层（Network Layer）**：
   - 负责感知数据的远距离可靠透明传输。包括移动通信网（5G/4G）、低功耗广域网（NB-IoT, LoRa）、卫星通信及互联网骨干网。
3. **应用层（Application Layer）**：
   - 结合行业业务场景实现智能化应用与决策分析（智慧城市、工业物联网 IIoT、智慧消防、车联网）。

### 13.6.2 防火报警器 SaaS：设备关系、事件存储与访问优化
[考查：案例分析（物联网数据建模、NoSQL 选型与性能优化）]

物联网 SaaS 面向消防机构、企业、社区/物业和个人用户，多客户共享平台时要把**租户隔离**与**设备授权关系**纳入模型。设备可被多个组织或用户共同监管，通常用设备—组织/用户关联表表示多对多关系，并在关系上保存租户、角色、授权范围和有效期，避免把单一“所属用户”字段当成完整授权模型。

数据按访问特征分工：MySQL 保存用户、租户、设备档案及需要事务一致性的业务记录；Redis 用于缓存、会话或最新设备状态等高频数据；海量心跳、遥测和告警历史按写入规模与查询方式选择时序/NoSQL 存储。题库建议以 MongoDB 替换 HBase，理由是 HBase（列族存储）不适合复杂关联查询；实际选型需看负载，HBase 可用于高吞吐追加和时间范围扫描，MongoDB 更适合灵活文档与多条件检索，不能脱离查询模式断言其中一种普遍更优。SSM 是应用框架，与多种存储并不冲突。

设备静态档案与频繁变动的当前状态可分开存储；心跳历史采用事件/时序记录，同时维护供在线查询的最新快照。告警本身与通知收件明细分开，一条告警可以生成多条用户通知，并分别记录接收对象、投递状态和时间。

| 性能策略 | 原理 | 成本 | 预期效果 | 常见实施 |
|---|---|---|---|---|
| 减少数据访问 | 减少磁盘访问 | 低 | 极好 | 反范式、适度冗余、增加缓存 |
| 返回更少数据 | 减少网络传输 | 低 | 好 | 分页、裁剪非必要返回字段 |
| 减少交互次数 | 减少网络往返 | 低 | 一般 | 批量访问，存储过程一次返回多组结果 |
| 减少 CPU 开销 | 减少 CPU 与内存开销 | 低 | 较差 | 优化业务逻辑 |
| 利用更多资源 | 增加可利用资源 | 高 | 极好 | 主从集群、命令查询分离 |

报警与联防业务应优先保证关键状态和告警数据的及时性。缓存要设置失效/更新策略；复制延迟期间，对读后立即读等一致性敏感请求应按业务要求访问主节点。

## 13.7 层次式架构案例分析

### 13.7.1 电子商务网站（网上商店 PetShop 经典分层架构） ⭐⭐
1. **经典分层布局（.NET 体系示范）**：
   - **表示层（Web Presentation）**：ASP.NET 页面与用户交互，仅依赖业务逻辑层与模型层。
   - **业务逻辑层（BLL）**：处理订单流转、库存校验，依赖抽象数据访问接口层（IDAL）。
   - **数据访问接口层（IDAL）**：定义持久化契约接口，解耦具体数据库实现。
   - **数据访问工厂层（DALFactory）**：采用**抽象工厂模式 + 反射**，根据 Web.config 配置动态实例化 SQL Server 数据访问层或 Oracle 数据访问层。
   - **具体数据访问层（SQLServerDAL / OracleDAL）**：实现 IDAL 接口，封装特定数据库的 SQL 与存储过程调用。
   - **通用业务实体层（Model）**：贯穿各层共享的贫血实体对象。
2. **核心启示**：通过依赖倒置（DIP）与接口驱动开发，实现业务逻辑与特定数据库厂商完全解耦。

### 13.7.2 SSH / SSM 轻量级 J2EE 分层映射（架构图填词案例） ⭐⭐
[考查：案例分析（分层架构图填词）]

- **五层链路**：视图层 → Web 层 → service 层（业务逻辑实现）→ DAO（数据访问对象）→ 持久层（ORM）→ 数据库服务。
- **框架 ↔ 层固定映射（SSH）**：**Struts2 = Web 层 MVC 控制器**（控制业务逻辑层与表现层的交互）；**Spring = 业务逻辑层**；**Hibernate = 持久层 ORM**（实体关系映射，由数据库得来对象）；视图层界面框架 = **SiteMesh**（页面布局/装饰）+ **jQuery**（JavaScript 框架，两空可互换不可重复）。
- **排除法**：题干"**轻量级** J2EE"→ 排除 **EJB**（重量级）；数据库品牌严格照题干（MySQL ≠ PostgreSQL）；"模型层"在分层链路中无独立框（业务数据由 service/DAO/持久层承载），常作干扰项。
