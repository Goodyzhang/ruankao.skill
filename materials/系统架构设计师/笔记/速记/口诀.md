# 系统架构设计师 · 做题口诀

按考察内容分类整理：口诀作标题，教材原文与讲解放小字。

## 软件工程 · 模块独立性（耦合与内聚）

### 「飞鼠掷镖失控，外公躲进屋内」—— 耦合度从低到高

- <small>对应：**飞**（**非**直接耦合）→ **鼠**（**数**据耦合）→ **镖**（**标**记耦合）→ 失**控**（**控**制耦合）→ **外**（**外**部耦合）**公**（**公**共耦合）→ 屋**内**（**内**部／内容耦合）。画面：飞鼠扔镖失了控，外面的外公吓得躲进屋内——事故越闹越大，耦合越来越高，且"外→公→内"借外公从屋外进屋内的动作收尾。</small>
- <small>流行变体：「鼠标控，外公内」（网上笔记常见，与本口诀同源但漏了非直接耦合）。</small>
- <small>非直接耦合：两个模块之间没有直接关系，联系完全通过主模块的控制和调用来实现。</small>
- <small>数据耦合：一组模块借助参数表传递简单数据。</small>
- <small>标记耦合（特征耦合）：一组模块通过参数表传递记录信息（数据结构）。</small>
- <small>控制耦合：模块之间传递的信息中包含用于控制模块内部逻辑的信息。</small>
- <small>外部耦合：一组模块都访问同一全局简单变量，且不是通过参数表传递该全局变量的信息。</small>
- <small>公共耦合：多个模块都访问同一个公共数据环境。</small>
- <small>内部耦合（内容耦合）：一个模块直接访问另一个模块的内部数据；不通过正常入口转到另一模块内部；两模块有部分代码重叠；一个模块有多个入口。</small>
- <small>考法一：对选项给出的几种耦合排序。考法二（2021 下第 46 题）耦合设计原则：尽量使用数据耦合、少用控制耦合和特征耦合、限制公共（环境）耦合的范围、完全不用内容耦合——原则顺序即按耦合从低到高取。</small>

### 「肛顺通，过时喽——呕！」—— 内聚度从高到低

- <small>对应：**肛**（**功**能内聚）→ **顺**（**顺**序内聚）→ **通**（**通**信内聚）→ **过**（**过**程内聚）→ **时**（**时**间／瞬时内聚）→ **喽**（**逻**辑内聚）→ **呕**（**偶**然内聚）。画面：通便神药"肛顺通"放过期喽，一吃就呕——药越往后越拉胯，内聚越来越低。</small>
- <small>清雅变体：「功顺通过时逻偶」；注意「通过」是两个词——通信 + 过程。网上流传的「偶逻功」「肛顺通」等均为残缺版（漏了最低的偶然内聚），勿用。</small>
- <small>方向提醒：与耦合口诀相反，内聚是从高到低背。</small>
- <small>功能内聚：完成一个单一功能，各个部分协同工作、缺一不可（最高）。</small>
- <small>顺序内聚：处理元素相关，而且必须顺序执行。</small>
- <small>通信内聚：所有处理元素集中在一个数据结构的区域上。</small>
- <small>过程内聚：处理元素相关，而且必须按特定的次序执行。</small>
- <small>瞬时内聚（时间内聚）：所包含的任务必须在同一时间间隔内执行。</small>
- <small>逻辑内聚：完成逻辑上相关的一组任务。</small>
- <small>偶然内聚（巧合内聚）：完成一组没有关系或松散关系的任务（最低）。</small>

## 软件工程 · 逆向工程

### 「师姐共浴」—— 逆向工程抽象级别从低到高

- <small>排序（由低到高）：**实**现级 → **结**构级 → **功**能级 → **域**（领域）级（「师姐共浴」谐音「实结功域」）。</small>
- <small>实现级（最低）：程序的代码细节与语法结构，典型产物为**语法树、符号表**。</small>
- <small>结构级：程序分量之间的相互依赖关系（谁依赖谁/调用谁），典型产物为**调用图、结构图**。</small>
- <small>功能级：程序段的功能及段间关系（程序行为），典型产物为**数据流模型、控制流模型**。</small>
- <small>领域级（最高）：程序实体与应用领域概念之间的对应关系（业务语义），典型产物为**业务模型、领域术语、ER 模型**。</small>
- <small>判别一刀：关系的另一端指向程序内部实体 → 结构级；指向业务领域概念 → 领域级；强调程序段功能与数据/控制流 → 功能级。</small>
- <small>完备性规律：抽象级别越高，完备性越低（语义丢失越严重，UML 状态图与部署图完备性最低）。</small>

## 软件工程 · 过程能力成熟度（CMMI）

### 「屎里已晾油」/「处馆腚凉油」—— CMMI 五级从低到高

- <small>排序（由低到高）：**初**始级（屎/处） → 已**管**理级/可重复级（里/馆） → **已**定义级（已/腚） → **量**化管理级（晾/凉） → **优**化级（油）。</small>
- <small>初始级（1级）：过程混乱无序不可预测，靠个人英雄主义救火，常延期超支。</small>
- <small>已管理级/可重复级（2级）：**单项目级**管控——需求受控，按计划执行并跟踪成本、进度、质量，能重复以往项目的成功。</small>
- <small>已定义级（3级）：**组织级/企业级**标准过程制度化、文档化，项目按组织流程剪裁执行，对整个流程严格监测、控制与审查（2021 下第 17 题考点）。</small>
- <small>量化管理级（4级）：建立**量化**的质量与子过程性能目标，利用统计技术控制过程（SPC）。</small>
- <small>优化级（5级）：跨项目采集数据，关注整体组织绩效，专注于**持续过程改进**与缺陷预防。</small>
- <small>做题一刀判词：**「项二企三数四改五」**——题干再怎么吹计划监控审查，落脚在「项目」就是 2 级；一旦出现「企业体系/流程制度/组织资产」必锁 3 级（已定义）；带数据统计选 4 级；持续改进缺陷预防选 5 级。</small>
- <small>命名陷阱：题库里第 2 级常写作「可重复级」（CMM 旧称），与 CMMI 的「已管理级」是同一级；但 CMM 旧版第 4 级也叫「已管理级」——同名不同级，看上下文用 CMMI 还是 CMM 叫法。</small>

## 软件工程 · 需求工程（开发 vs 管理）

### 「开发活粉定验，管理2控2跟」—— 需求工程两大家族

- <small>需求开发（生孩子·从无到有）：**获**取 → **分**析 → **定**义（规格说明） → **验**证（评审） → **「活粉定验（获分定验）」**。</small>
- <small>需求管理（管孩子·防走样）：**「2 控 2 跟踪」** → **变**更控制、**版**本控制、需求**跟**踪、需求**状**态跟踪（2021 下第 19 题考点）。</small>
- <small>做题一刀判词：选项出现获取/分析/定义/验证是「开发」；出现控制/跟踪是「管理」。</small>

## 软件工程 · 软件配置管理（SCM）

### 「稳成逼数」—— 产品配置（配置项）四大组成要素

- <small>四大范畴：**文**档、计算机**程**序、**部**件、**数**据（谐音**「稳成逼数」**，2021 下第 18 题考点）。</small>
- <small>产品配置定义：一个产品在其生命周期各个阶段所产生的各种形式（机器可读或人工可读）和各种版本的**文档、计算机程序、部件及数据**的集合。</small>
- <small>注意防坑：选项常罗列具体文档（如需求说明、设计说明、测试报告、用户手册等）报菜名忽悠人；记住产品配置考的是顶层四大集合分类，心里要有「稳成逼数（文程部数）」直接秒选大杂烩！</small>

## 软件工程 · 软件生命周期

### 「定期开运维」/「一发运维」—— 传统软件生命周期阶段划分

- <small>四个阶段：软件**定**义 → 软件**开**发 → 软件**运**行 → 软件**维**护（首字谐音**「定开运维 / 定期开运维」**，尾字谐音**「一发运维（义发运维）」**，2021 下第 21 题考点）。</small>
- <small>传统大三阶段：标准划分为 3 个大时期——软件定义期、软件开发期、软件运行与维护期（本题将运行和维护拆开作为两个小阶段）。</small>
- <small>软件定义期：问题定义、可行性研究、需求分析。</small>
- <small>软件开发期：总体设计（概要设计）、详细设计、编码、**测试**。</small>
- <small>软件运行与维护期：长期运行部署与纠错、适应、完善、预防性维护。</small>
- <small>头号巨坑（防错必看）：**绝无「软件测试」顶级阶段！** 40% 的考生误选包含「测试」的选项——记住**测试被开发包养在肚子里**，只是开发阶段的一个子环节，根本不配在顶级生命周期里自立门户！</small>

## 软件工程 · 统一过程（RUP）

### 「尚需分设实测部，支持记得配项环」—— RUP 9 大核心工作流（6 过程 + 3 支持）

- <small>6 个核心过程工作流（研发主线）：**「尚需分设实测部」** → **商**业建模（尚） → **需**求 → **分**析和**设**计 → **实**现 → **测**试 → **部**署。</small>
- <small>3 个核心支持工作流（后勤保障）：**「配项环」（赔光环）** → **配**置和变更管理 → **项**目管理 → **环**境。</small>
- <small>考法防坑：考题常将支持工作流混入过程工作流中考察分类。记住后勤保障要**「配项环」**（配置、项目、环境），其余全属于主线过程！</small>

### 「促膝勾引」与「用假爹」—— RUP 4 阶段与 3 大核心特征

- <small>4 个阶段（由先到后）：**初**始阶段 → **细**化阶段 → **构**造阶段 → **移**交阶段（谐音**「促膝勾引」**）。</small>
- <small>4 阶段核心任务与陷阱：
  - 初始阶段：做商业论证、定项目范围，里程碑是生命周期目标（LCO）。
  - **细化阶段（高频命题点）**：分析领域、消除高风险、**建立完善的架构基线**，里程碑是生命周期架构（LCA）。**绝非在初始阶段定架构！**
  - 构造阶段：开发剩余构件、集成测试，里程碑是初始运行能力（IOC）。
  - 移交阶段：测试、分发、培训用户，里程碑是产品发布（PR）。</small>
- <small>3 大核心特征：**用**例驱动、以**架**构为中心、**迭**代和增量（谐音**「用假爹」**）。</small>

## 软件工程 · 构件（Component）

### 「竹鼠档毒镖」—— 构件的五大特性

- <small>对应：**竹**（可**组**装性）→ **鼠**（可部**署**性）→ **档**（文**档**化）→ **毒**（**独**立性）→ **镖**（**标**准化）。可联想：竹鼠在档口耍毒镖。</small>
- <small>可组装性：构件的所有外部交互必须通过**公开定义的接口**进行，同时还必须对自身信息提供外部访问。</small>
- <small>可部署性：构件必须是**自包含**的，能够作为独立实体在构件平台上运行，以**二进制形式部署而无需编译**。</small>
- <small>文档化：构件必须完全文档化，便于使用者了解构件的功能、接口及使用方法。</small>
- <small>独立性：构件是一个**独立的软件单元**，能够独立部署和组装。</small>
- <small>标准化：构件的接口、组装与部署等应遵循相应的标准或规范，以保证复用和互操作。</small>
- <small>真题提醒（2024 上第 25 题）：「二进制形式、部署前无需编译」是**正确**描述；「不能对构件进行配置来适应应用系统」是**错误**描述——构件可通过配置适应具体应用系统，因此该题选此项。</small>

## 架构设计 · 4+1 视图模型

### 「开逻进物场」—— 4+1 视图的五个视图

- <small>对应：**开**发视图、**逻**辑视图、**进**程视图、**物**理视图、**场**景；教材讲解顺序为逻辑→开发→进程→物理+场景，口诀只是帮助记全，不代表高低顺序。</small>
- <small>特征钩子（配套口诀「开组，逻对，过并」）：开发→模块**组**织管理；逻辑→类图/**对**象图；进程→**并**发性。</small>
- <small>逻辑视图：主要支持系统的**功能需求**，即系统提供给最终用户的服务；一般用**类图和对象图**描述。</small>
- <small>开发视图（模块视图，UML 中称**实现视图**）：侧重软件模块的组织和管理；可描述源代码、系统文件结构。</small>
- <small>进程视图：侧重系统**运行特性**，关注非功能性需求（性能、可用性等）；强调**并发性、分布性、系统集成性和容错能力**；定义逻辑视图中各个类的操作具体在哪个线程中执行。</small>
- <small>物理视图（UML 中称**部署视图**）：考虑如何把软件**映射到硬件**上，解决系统拓扑结构、安装、通信等问题；软件到节点的映射要有较高灵活性，环境改变时对系统其他视图影响最小化。</small>
- <small>场景（"+1"）：重要系统活动的抽象，使四个视图有机联系起来，是最重要的**需求抽象**；对应 UML 中的**用例视图**。</small>
- <small>常考名称对应：开发视图＝实现视图，物理视图＝部署视图，场景＝用例视图；见"并发/性能/线程"→进程视图，见"映射到硬件/节点"→物理视图。</small>

## 架构设计 · 特定领域软件架构（DSSA）

### 「垂直一多，水平多多」—— DSSA 垂直域与水平域

- <small>对应：垂直域 ＝ **一**个（特定）系统族 → 族内**多**个系统；水平域 ＝ **多**个系统 ＋ **多**个系统族的共有部分。</small>
- <small>垂直域：定义了一个特定的系统族，包含整个系统族内的多个系统，可作为该领域系统可行解决方案的一个**通用软件架构**；关注与行业相关、聚焦**行业特性**的内容（行业纵深）。</small>
- <small>水平域：定义了在多个系统和多个系统族中**功能区域的共有部分**，在**子系统级**上涵盖多个系统族的特定部分功能；关注各行业**共性**部分的内容（跨行业通用）。</small>
- <small>判别一刀：题干见"一个特定系统族 / 整个行业"→ 垂直域；见"多个系统族 / 共有部分 / 共性"→ 水平域（2021 下第 40 题：(40) 垂直域、(41) 水平域）。</small>

## 架构设计 · 架构评估（ATAM 场景）

### 「刺儿环里响」—— 场景描述三要素

- <small>对应：**刺**（刺激 stimulus）掉进**环**（环境 environment）里叮当作**响**（响应 response）；动作链即答案顺序，「环里」的"环"字帮你排掉干扰项"制品"。</small>
- <small>场景（scenarios）：体系结构评估时，为精确得出具体质量目标并以此判定体系结构优劣而采用的机制；是从**风险承担者**的角度对与系统交互的简短描述（2021 下第 53 题答案：风险承担者）。</small>
- <small>评估中一般用**刺激、环境、响应**三方面描述场景（2021 下第 54 题）。</small>
- <small>易混区分：完整**质量属性场景**为六要素——刺激源、刺激、环境、制品、响应、响应度量；干扰项里的"刺激源、制品"正是六要素的零件。记法：「**源**刺环**制**响**度**」（源＝刺激源、制＝制品、度＝响应度量）。考"评估中场景描述"选三要素，考"质量属性场景"选六要素。</small>

## 信息化 · 数字化转型

### 「战运鸡」—— 信息化需求三层次

- <small>对应：**战**略需求 → **运**作需求 → **技**术需求（「鸡」谐音「技」）。</small>
- <small>战略需求：组织信息化的目标是提升组织的竞争能力、为组织的可持续发展提供一个支持环境；信息化对组织不仅仅是服务的手段和实现现有战略的辅助工具，还可以把组织战略提升到一个新的水平，为组织带来新的发展契机；特别是对企业，信息化战略是企业竞争的基础。</small>
- <small>运作需求：组织信息化需求非常重要且关键的一环，包含三方面——一是实现信息化战略目标的需要；二是运作策略的需要；三是人才培养的需要。</small>
- <small>技术需求：由于系统开发时间过长等问题，在信息技术层面上对系统的完善、升级、集成和整合提出的需求；原来基本没有大型信息系统项目、只有一些单机应用的组织，其信息化需求一般是从头开发新的系统。</small>

### 「初单流网生」—— 数字化转型五阶段

- <small>阶段从低到高：**初**始级 → **单**元级 → **流**程级 → **网**络级 → **生**态级</small>
- <small>初始级：在单一职能范围内初步开展了信息（数字）技术应用，但尚未有效发挥信息（数字）技术对主营业务的支持作用。</small>
- <small>单元级：在主要或若干主营业务单一职能范围内开展了（新一代）信息技术应用，提升相关单项业务的运行规范性和效率。</small>
- <small>流程级：在业务线范围内，通过流程级数字化和传感网级网络化，以流程为驱动，实现主营业务关键业务流程及关键业务与设备设施、软硬件、行为活动等要素间的集成优化。</small>
- <small>网络级：在全组织（企业）范围内，通过组织（企业）级数字化和产业互联网级网络化，推动组织内全要素、全过程互联互通和动态优化，实现以数据为驱动的业务模式创新。</small>
