# 论文得分笔记：旧课与专题 3、4 合订

论文要让阅卷者看见三件事：**题目要求回答了；原理和机制成立；本人在具体业务中作出了决策并验证结果。** 结构清楚帮助呈现这些内容，技术名词和完整模板不能代替论证。

## 一、把之前学过的结构固定下来

| 段次 | 写什么 | 练笔预算 |
| --- | --- | ---: |
| 1—2 | 摘要：项目与职责；本题三组措施、用途和效果 | 约 300 字 |
| 3—4 | 建设原因；项目功能、相关技术、规模及本人职责 | 约 500 字 |
| 5 | 按原题顺序回应子题二全部要求，再引出实践 | 约 300 字 |
| 6—8 | 三组论点，每组结合业务写判断、措施、过程和验证 | 约 1050 字 |
| 9—10 | 完成状态、成效与经验；一至两个不足及对应改进 | 约 350 字 |

专题 3 给出的区间为摘要约 300 字、背景 400—600 字、子题回应 300—400 字、主体 1000—1500 字、收尾 300—500 字。区间用于安排篇幅，不把每项上限相加当目标。我们的常用训练仍按摘要约 300 字、正文约 2200 字组织，具体题卷要求优先。

## 二、新课最需要记住的论证链

**题目 → 小问 → 段落主张 → 业务实例 → 验证效果。**

检查时依次读：题目让你说明什么；这一段准备证明什么；例子实际展示了什么；最后的结果测量了什么。发现断点，修改断点。

| 容易写偏的地方 | 不能只写 | 应该写到 |
| --- | --- | --- |
| 高并发题使用微服务 | 独立部署、团队并行、技术异构 | 哪个高峰业务形成瓶颈，拆分后如何隔离负载或独立伸缩，同条件时延、吞吐或资源争用怎样变化 |
| 六边形架构结合 DDD | 统一语言、限界上下文、聚合 | 这些分析如何识别业务核心；输入输出端口、适配器及依赖方向怎样设计，外部替换如何验证 |
| LLM 测试用例生成 | 单元、集成、系统测试各是什么 | 输入哪条需求或代码，怎样约束模型输出，用例参数与预期是什么，如何审核、运行和反馈 |
| 面向对象分析 | 参与者、用例、类名的长清单 | 一个用例的正常及替代流程，一组业务概念的关系和职责，一个实体的事件与状态转换 |
| 架构风格 | 产品名与数据库清单 | 构件、连接件、组织约束及业务协作，说明组合风格分别落在哪里 |

正文段首可以用业务挑战点题，帮助读者理解。全文已经建立清楚对应关系时，不必每段重复题目词；给偏题段补几个“高并发”字样，也不能补出真正的论证。

## 三、子题二全部回应，子题三实例写深

五项、六项要求全部有明确落点，再选重点或组合成三组实践。题目若要求全部方面结合项目展开，按该要求执行。主体已经逐项完成时，不为形式重复增加概述段。

写实例时准备这几个要素：业务角色与目标、输入、规则或状态、本人判断、处理与交互、输出、验证。原理一两句即可，主要篇幅用于项目怎样做。

只写“模型生成用例，效率提高 60%”，仍缺少实现过程。只写一次配置服务故障，也不能自动证明故障是由 LLM 生成的用例发现。

## 四、摘要、背景和结尾各负其责

- **摘要前半**：项目做什么，本人负责什么。功能概括即可，避免占用全部字数。
- **摘要后半**：明确本题论题，按正文顺序概括三组措施及用途，效果必须在正文有落点。团队任务清单不能替代正文概括。
- **背景第一段**：旧流程有什么问题，为何建设项目。背景第二段解释相关功能、技术与本人职责，避免只列模块和中间件。
- **主体**：每段一个可辨认的主张，理论与业务过程连在一起，不能先列全部技术，再孤立列全部效果。
- **结尾**：效果回扣论题，不足具体且配改进。开发周期缩短证明交付效率，不能独自证明查询性能或数据一致性。

学习稿可以有段号、表格和“背景”等辅助标签；考场正文应连续成文。题卷或输入框本来要求的“摘要”“正文”区块正常保留。技术小标题属于表达选择，不能据此推断作者用了 AI 或直接判不合格。

## 五、课堂高分稿也要再查机制

| 课堂材料中的风险写法 | 应检查或修正 |
| --- | --- |
| 接口类、实现类、工具类、VO 类作为概念类 | 先识别业务实体、关系、职责；实现分类不能代替需求分析模型 |
| 包含、扩展关系写成参与者与用例之间关系 | 区分参与者与用例的关联，以及用例间的包含、扩展、泛化 |
| 用了 Redis、消息队列就“保证一致” | 交代权威状态、事务边界、投递与确认、幂等、版本及恢复对账 |
| 使用多个数据库、统一 DAO 就称仓库风格 | 检查共享逻辑模型、中央数据及各构件围绕数据的协作方式 |
| KEDA 被当作节点扩容器 | 区分事件指标驱动工作负载扩缩与节点容量供给；配合 HPA、节点伸缩器说明各自职责 |
| 有状态服务一概不能容器化 | 解释会话、存储、迁移和排空等条件，不能把一次选型写成普遍定律 |
| 自动伸缩被说成线性增容 | 核对共享瓶颈、调度准备和冷启动，效果用压测验证 |
| 事务成功率证明强一致，受理耗时证明完成耗时 | 成功率、一致性、受理时延和最终完成时延分别确定对象 |

课堂中的口语强调帮助识别重点；题面范围与技术机制仍要独立核对。不把“看到标题就不过”“AI 已经怎样阅卷”等说法变成评分规则。

## 六、批改时怎样给分才有用

先画逐项覆盖表，再给判断。每条意见包含：**位置与原句 → 对应要求 → 实际断点 → 影响 → 替换稿**。改后重新核对摘要、主体、结尾，不让新指标只留在其中一处。

本轮统一训练表：题意与要求覆盖 20、理论及机制正确 20、业务实践与本人决策 20、结果验证与自洽 10、结构表达 5，共 75 分。课件标注分、老师自估和本轮训练分分开记录；评分不按课堂成绩倒推。

未展示、未还原与确认漏答分开。局部材料只给可评部分得分和分母；未知项保留，不凭缺图判零。八段、十段、混合架构、产品数量及应试模拟缺真实仓库，都不能自动决定合格与否。

## 七、十二条规则的课堂对照

| 规则 | 学习后要执行的动作 | 课堂对照 |
| --- | --- | --- |
| P01 审题对象 | 保留原题对象、动词和范围 | 高并发写成微服务；LLM 生成写成测试阶段定义 |
| P02 论证相关性 | 核对主张、实例和结果间的关系 | 高并发低分组与 47、48 分组对照；混合风格误批 |
| P03 要求覆盖 | 全部方面有落点，重点再深入 | 六类并发手段；ABSD 六项活动；三类需求评审 |
| P04 实例与行动 | 选择一个业务过程展开 | SRM 用例、类模型与动态模型；LLM 具体需求转用例 |
| P05 效果因果 | 用直接指标验证本段措施 | 回测开发效率与并发性能；事务成功率与一致性 |
| P06 技术正确 | 通过稿和 AI 示范也独立核对 | 缓存消息、伸缩层级、概念类、仓库风格 |
| P07 项目背景 | 解释功能和技术作用 | 高并发与车辆仿真稿的模块罗列、背景失序 |
| P08 摘要对应 | 从正文回填论题、主张、效果 | 摘要只写团队职责或连续强调微服务 |
| P09 结尾闭合 | 成效扣题，不足配改进 | 需求评审稿结尾兼容和压测问题需联系评审漏项 |
| P10 材料完整性 | 未还原保留待核 | LLM 39 分片段缺摘要；多篇子题二未还原 |
| P11 写作口径 | 模拟稿按设定改好，元数据与正文分开 | AI 构造背景、结尾和实施细节，继续沿用授权 |
| P12 证据评阅 | 每个问题能定位，修改后回填 | 课堂范文试评、六组合成短例与四份独立试用 |
