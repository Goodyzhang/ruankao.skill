# 个性化应试模拟论文

默认写完整应试作文。允许以已有业务背景设计论题要求的技术、职责、实施过程、困难和效果，不因缺真实实施记录而停在提纲。用户明确要真实经历版本时才收紧事实范围。本模式不改变 prep 的真实素材规则。

1. 保存完整论题、逐项要求、网站要点/范文与题源。参考其方法，创作自己的文章。
2. 从已绑定资料提取业务特色，优先用户已有水质预测/水环境背景；按论题设计 Redis、微服务或航天器水循环监测等项目。无资料时建立具体模拟项目，不强求真实证据。
3. 保存本批模拟设定：名称、阶段、工期、规模、本人角色、关键架构、质量目标与结果。各篇沿用；需演进时说明阶段，避免规模、角色或架构互相冲突。
4. 先做题面覆盖表，设计每项的概念、本人行动、困难、选择、取舍、效果，再写摘要和全文。题面限字优先；未规定时训练目标摘要约300字、正文约2300字，不称官方要求。
5. 复核扣题、术语、可行性、项目特色、本人职责、数据/时间一致性及字数。把“提高效率”展开为具体行动和合理效果，不堆产品清单。

写 Redis 要有缓存对象、键/TTL、读写一致性、热点与回源；写微服务要有业务边界、调用/数据关系、治理和拆分代价。关键实践说明“问题→选择→实施→结果→反思”。模拟指标须口径一致、规模合理、措施能解释变化；专业原理仍核验。

全文存科目论文目录，题源/网站解析存题库。元数据和独立写作说明标 exam-simulation；正文采用完整第一人称考场作文，不反复插事实边界、待证实或免责声明。说明另列覆盖表、设定、字数、技术来源和自审。不得覆盖原始项目底稿、真实经历或把模拟设定回写为真实个人事实。学习辅助图与全文分开，全文可用纯文字完整扣题。

数据流复核要区分重试与有意重算：幂等身份覆盖模型版本与输入数据版本；历史修正不能被旧去重键吞掉。事务消息表的行与业务更新同事务提交，提交后才投递，不写成提交后另建消息。跨服务查数据通过拥有该数据的服务或读模型，不能在论述边界之后又隐含越界直读数据库。参考 [AWS transactional outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html) 核验消息与事务边界。
