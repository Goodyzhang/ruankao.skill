## 案例一：MVC 架构分析与 MIS 设计

### 阅读以下关于 MVC 架构的说明，回答问题 1 至问题 3。

**说明**：
某软件公司欲开发一个小学英语智能学习系统，小明可以使用该系统在 Web 页面上学习英语，每个学习单元包含 10 个单词和 20 句子。小明需要按照学习计划在 20 天内完成一个学习单元的完整学习。在学习过程中，系统会展示学习进度条显示当前学习进度。另外，如果小明答对 3 题及以上，系统会在数据库中记录小明的学习成功记录；答对 3 题以下，系统会提示小明继续努力。

该系统采用 MVC（Model-View-Controller）架构。Controller 是系统的控制中心，负责接收用户请求并转发给相应的 Model 进行处理；Model 是应用业务逻辑的主体，负责处理业务数据和业务规则；View 负责展示用户界面，包括 HTML 页面和 Controller 响应。

系统要求支持 300 个并发用户，每个 Controller 请求的平均响应时间应小于 3 秒。Controller 采用 Java Servlet 技术，Model 采用 JDBC 技术，View 采用 JSP 技术。

**MVC 架构说明（Smalltalk-80）**：

```
┌─────────┐     ┌─────────────┐     ┌─────────┐
│  View   │←───→│ Controller  │←───→│  Model  │
│  视图   │     │   控制器     │     │  模型   │
└─────────┘     └─────────────┘     └─────────┘
     ↑                                    ↑
     └────────────────────────────────────┘
              用户交互与数据更新
```

- **Model（模型）**：封装应用业务逻辑和数据。模型对象负责在数据库中存取数据。
- **View（视图）**：负责呈现模型创建的数据。视图将模型中的数据可视化。
- **Controller（控制器）**：接收用户输入，更新模型并选择视图。

│     └───►│   数据存储     │◄────────┘              │

## 案例三：宇航嵌入式设备 TLS 架构、操作系统选型与故障处理（25分）

### 阅读以下关于宇航嵌入式设备软件总体架构的描述，回答问题 1 至问题 3。

**【说明】**

某公司承担了一项宇航嵌入式设备的研制任务。本项目除对硬件设备环境有很高的要求外，还要求支持以下功能：
（1）设备由多个处理机模块组成，需要时外场可快速更换（即 LRM 结构）；
（2）应用软件应与硬件无关，便于软硬件的升级；
（3）由于宇航嵌入式设备中要支持不同功能，系统应支持完成不同功能任务间的数据隔离；
（4）宇航设备可靠性要求高，系统要有故障处理能力。

公司在接到此项任务后，进行了反复论证，提出三层栈（TLS）软件总体架构，如下图所示，并深入分析了操作系统选型、数据隔离和故障处理等关键技术。

### 问题 1（7分）

**TLS 架构具有什么特点？请说明各层的具体内涵。**

#### 【参考答案】

1. **TLS 架构的核心特点（3分）**：
   - **分层解耦与独立性**：将系统自顶向下清晰解耦为应用层、操作系统层和模块支持层三层体系，层间单向调用、职责单一；
   - **软硬件无关性（高可移植与可升级性）**：应用层通过标准 API（如 POSIX）与操作系统交互，不直接访问硬件；操作系统通过模块支持层（MSL）访问硬件，使应用软件与底层硬件完全解耦，支持软硬件各自独立升级；
   - **硬件抽象与快速维护（支持 LRM）**：模块支持层将异构硬件抽象封装为统一标准化接口，使得处理机硬件模块可以在外场实现即插即用的快速更换（LRM）。

2. **各层的具体内涵（4分）**：
   - **应用层（AL, Application Layer）**：由实现具体宇航业务逻辑的多任务/多进程组成（如姿态控制、轨道计算、遥测遥控等）。各任务的数据隔离与协同调度由操作系统层统一提供保障。
   - **操作系统层（OSL, Operating System Layer）**：介于应用层与模块支持层之间，向上提供标准化系统调用接口（如 POSIX API），屏蔽硬件平台的差异；向下调度管理计算资源，提供多任务并发调度、进程间通信、内存管理以及**关键任务间的数据与空间安全隔离**。
   - **模块支持层（MSL, Module Support Layer）**：直接面向底层物理硬件平台（类似 BSP/HAL 硬件抽象层）。负责硬件初始化、板级驱动程序、底层中断分发和物理总线管理，将具体处理机的物理特性封装成标准接口供操作系统调用，是**实现 LRM（外场可更换模块）物理与逻辑解耦的关键层**。

#### 【得分点与采分标准】（共 7 分）
- **TLS 特点（3分）**：答出“软硬件无关/解耦/高移植性”得 1 分；答出“分层独立/清晰/易升级维护”得 1 分；答出“支持 LRM/外场快速更换/硬件抽象”得 1 分。
- **各层内涵（4分）**：
  - 应用层：答出“完成具体宇航业务功能/由多任务组成/业务逻辑”得 1 分；
  - 操作系统层：答出“提供标准 API/屏蔽硬件差异/资源调度与数据隔离”得 1.5 分；
  - 模块支持层：答出“硬件抽象/驱动与初始化/支撑 LRM 外场快速更换”得 1.5 分。

### 问题 2（11分）

**王工和李工对操作系统选型产生了分歧。王工建议采用 VxWorks 5.5，李工建议采用嵌入式 Linux。**

**(1) 请根据下表中的对比，填写空白处 ①~⑤ 的内容（6分）。**

**表 3-1 VxWorks 5.5 与 Linux 的比较（题干原表）**

| 比较类型 | VxWorks 5.5 | Linux |
|:---|:---|:---|
| **工作方式** | 操作系统与应用程序处于同一存储空间 | ① |
| **多任务支持** | 多支持任务 (线程) 操作 | ② |

**(2) 根据题目中的功能需求，应选择哪种操作系统？请说明理由（5分）。**

#### 【参考答案】

**(1) 表格填空 ①~⑤ 完整对比表（6分）**：

| 比较类型 | VxWorks 5.5 | Linux |
|:---|:---|:---|
| **工作方式** | 操作系统与应用程序处于同一存储空间 | **① 操作系统与应用程序处于不同存储空间（内核态与用户态分离）** |
| **多任务支持** | 多支持任务 (线程) 操作 | **② 支持多进程、多线程操作** |
| **实时性** | **③ 硬实时系统（Hard Real-Time）** | 实时系统（软实时/弱实时） |
| **安全性** | **④ 任务间无隔离保护（单一平坦地址空间）** | **⑤ 支持进程间隔离保护（MMU 虚拟内存保护）** |
| **标准 API** | 支持 | 支持 |

- **①**：操作系统与应用程序处于不同存储空间（或 内核态与用户态分离 / 不同地址空间）
- **②**：支持多进程、多线程操作（或 多进程支持）
- **③**：硬实时系统（或 硬实时 / 强实时系统）
- **④**：任务间无隔离保护（或 无内存保护 / 单一平坦内存空间）
- **⑤**：支持进程间隔离保护（或 利用 MMU 隔离 / 进程虚拟地址保护）

**选型结论（2分）**：
应选择**类似于 Linux 的操作系统**（或具备进程级独立虚拟地址空间与强隔离保护能力的操作系统）。

**选型理由（3分）**：
1. **满足需求（3）不同功能任务间的数据强隔离要求（核心得分点）**：
   - VxWorks 5.5 采用单一平坦内存模型（Flat Memory），操作系统与所有任务共享同一地址空间，无内存保护单元（MMU）隔离，任何任务指针越界或内存踩踏均会破坏其他任务数据甚至崩溃内核；
   - Linux 支持内核态与用户态分离，每个进程通过硬件 MMU 映射到相互独立的虚拟地址空间，进程间互不干扰，**从硬件机制上天然满足宇航设备对不同功能任务间数据隔离的强制需求**。
2. **满足需求（4）高可靠性与故障防扩散要求（核心得分点）**：
   - 在 Linux 体系下，当某个非关键业务任务发生段错误或死循环等故障时，仅导致该用户态进程退出崩溃，操作系统内核与其它独立进程不受波及，系统可捕获异常并实施进程级重启自愈，**有效防止单点故障扩散**，契合宇航设备对高可用与可靠性的严苛标准。
3. **满足需求（1）与（2）的解耦与标准支持**：
   - Linux 具备成熟完备的驱动设备模型与标准 POSIX API 接口，与 MSL 配合能够很好地支持硬件模块插拔解耦（LRM）和应用软件平滑移植。

#### 【得分点与采分标准】（共 11 分）
- **表格填空 ①~⑤（6分）**：
  - ①（1分）：答出“处于不同存储空间”或“内核态与用户态分离/不同地址空间”；
  - ②（1分）：答出“支持多进程、多线程操作”或“多进程支持”；
  - ③（1分）：答出“硬实时系统”或“硬实时/强实时”；
  - ④（1.5分）：答出“任务间无隔离保护”或“无内存保护/无地址空间隔离”；
  - ⑤（1.5分）：答出“支持进程间隔离保护”或“利用 MMU 隔离/进程虚拟内存保护”。
- **选型与理由（5分）**：
  - 选型（2分）：明确选择 Linux（或类似 Linux 的多进程隔离系统）；
  - 理由（3分）：紧扣需求（3）和需求（4），答出“Linux 具备 MMU 虚拟地址空间隔离/进程数据强隔离”得 1.5 分；答出“用户态内核态分离/单进程故障不波及整机/提高可靠性”得 1.5 分。

**(1) 嵌入式系统常见故障的三种分类（3分）**：
- **硬件故障**：包括处理器 CPU 故障、存储器位翻转（单粒子翻转 SEU）、总线通信故障、电源及传感器等外设硬件损坏或异常；
- **应用软件故障**：包括计算溢出、除以零、死循环、野指针非法内存访问、任务超时、逻辑控制缺陷等；
- **操作系统/系统软件故障**：包括内核死锁、系统资源枯竭（堆栈溢出/内存泄漏）、设备驱动崩溃、进程调度异常、权限违规等。\
*(注：若从故障时态角度回答“瞬态故障/瞬时故障、间歇性故障、永久性故障”，同样属于工程经典分类，可酌情给分，但宇航分层体系中以软硬件层次分类为官方首选)*。

**(2) 常见故障滤波算法（列举两种即可，2分）**：
- **门限算法（阈值滤波法）**：设定容忍阈值，仅当异常采样值连续超出幅值门限时才触发故障认定；
- **递增/递减算法（计数器滤波法）**：检测到一次故障信号计数器加 $M$，检测到正常信号计数器减 $N$，计数器达到上限门限才确认为真实故障；
- **周期滤波算法（滑动时间窗口滤波）**：在固定监测时间周期内，统计故障出现的次数或持续时长占比，达标后方认定故障；
- **均值滤波算法 / 加权移动平均滤波**：对连续采样数据进行平滑处理，滤除瞬态单粒子翻转带来的偶发脉冲干扰。

**(3) 常见容错算法与策略（列举三种即可，2分）**：
- **双机热备（Hot Standby）/ 双机冷备（Cold Standby）**；
- **三模冗余（TMR, Triple Modular Redundancy）/ 多模冗余与表决机制**；
- **N+1 备份冗余（N+1 Redundancy）**；
- **故障检测、隔离与重组（FDIR）机制**；
- **检查点恢复与状态回滚（Checkpointing & Rollback）**；
- **降级运行（故障降额/安全保护模式）**。

### 💡 深度技术解析与方法论

#### 1. 宇航嵌入式系统的核心矛盾与 TLS 架构的破局之道
- **传统单体 RTOS（如 VxWorks 5.5）的软肋**：
  在早期的嵌入式军工/宇航装备中，追求极致的执行速度和极小的内存占用，操作系统采用**平坦内存模型（Flat Memory）**，应用与内核同处一个特权级空间，通过函数直接调用。但其致命缺陷在于：**“一损俱损”**。一旦一个非关键遥测任务由于宇宙辐射或代码 bug 出现空指针野指针写入，整个内存空间被污染，飞控核心调度瞬间瘫痪。
- **TLS（Three-Level Stack）分层机制的核心思想**：
  - **MSL 向上隔离硬件异构性**：宇航 LRM（外场可更换模块）要求支持插拔更换不同的 CPU 板卡（如从 PowerPC 升级到国产龙芯/飞腾），MSL 统一将底层寄存器和总线抽象，使 OS 无感知；
  - **OSL 向下屏蔽硬件，向上提供隔离**：引入带硬件 MMU 保护的现代操作系统内核，通过特权级与虚拟地址划分出沙箱进程空间；
  - **AL 业务模块自治**：飞控、导航、载荷、通信各居其位，数据交互必须经由 POSIX IPC 管道或共享内存受控传递，实现了宇航级高安全。

#### 2. 案例分析论述题解题方法论（宇航/嵌入式答题套路）
1. **题干需求逐条映射法**：
   - 看到题干给出了带编号的功能需求（1）（2）（3）（4），在作答“架构特点”与“系统选型理由”时，**必须显式引用原需求编号**（如“针对需求（3）...，针对需求（4）...”），这是阅卷老师在采分点上的首要抓手。
2. **表格填空的对仗与特异性法则**：
   - 对比表格必然存在对称性：
     - 左侧写“操作系统与应用程序处于同一存储空间”，右侧必然填写“**处于不同存储空间（内核态与用户态分离）**”；
     - 左侧写“多支持任务(线程)”，右侧必填“**支持多进程、多线程**”；
     - 右侧写“实时系统”，左侧必填“**硬实时系统**”；
     - 左侧写“任务间无隔离保护”，右侧必填“**支持进程间隔离保护（MMU 保护）**”。
3. **宇航高可靠性“三部曲”专用术语**：
   - **故障检测与去噪**：瞬态单粒子脉冲 $\to$ 使用**门限滤波 / 递增递减计数器滤波**，防止假报警；
   - **故障隔离**：利用 **MMU 虚拟内存与特权级**，防止故障波及整机；
   - **故障恢复与容错**：采用 **TMR 三模冗余表决、双机热备、检查点回滚、降级运行**。

## 案例四：软件可靠性与容错设计

### 阅读以下关于软件可靠性设计的说明，回答问题 1 至问题 2。

**说明**：
某航空电子系统要求具有高可靠性，系统采用冗余设计来提高可靠性。系统包含两条独立的工作通道，每条通道的可靠度为 R。每条通道的失效率 λ = 0.0001 /小时。

系统可靠性设计方法包括：
1. **冗余设计（Redundancy）**：增加额外的硬件或软件副本
2. **容错设计（Fault Tolerance）**：在故障发生时继续提供服务
3. **故障检测与诊断（Fault Detection and Diagnosis）**：及时发现并定位故障

**FTA（故障树分析）** 和 **FMEA（失效模式与影响分析）** 是两种主要的可靠性分析技术。

### 问题 1

阅读上述说明，请给出系统可靠度 R 的计算公式，并计算系统工作 8760 小时（约 1 年）后的可靠度。

**解答**：
- 单通道可靠度：R = e^(-λt) = e^(-0.0001×8760) = e^(-0.876) ≈ 0.416
- 双通道冗余（并联）系统可靠度：R_s = 1 - (1-R)² = 1 - (1-0.416)² = 1 - 0.341 ≈ 0.659

### 问题 2

阅读上述说明，请说明 FTA 和 FMEA 在可靠性分析中的作用，并比较两者的优缺点。

**解答**：
- **FTA（故障树分析）**：自顶向下，从系统失效事件出发，分析导致失效的原因组合。采用演绎法，适合分析复杂的失效组合逻辑。
- **FMEA（失效模式与影响分析）**：自底向上，从组件失效模式出发，分析其对系统的影响。采用归纳法，适合识别单点故障和连锁失效。
- **FTA 优点**：能处理复杂的多重失效组合；缺点：难以穷举所有失效路径
- **FMEA 优点**：系统化、结构化；缺点：难以处理失效组合的乘法效应

## 案例五：LAMP Web 架构与性能优化

### 阅读以下关于 LAMP 架构的说明，回答问题 1 至问题 3。

**说明**：
某互联网公司采用 LAMP（Linux + Apache + MySQL + PHP）架构构建 Web 应用系统。系统上线后，Web 服务器出现 I/O 性能瓶颈，响应时间从设计的 200ms 上升到 800ms。

系统架构师提出了以下优化方案：
1. 在 Web 服务器和 MySQL 之间增加 Memcached 缓存层
2. 启用 MySQL 查询缓存（Query Cache）
3. 使用主从复制分担读负载

**LAMP 架构图**：

```
┌─────────────────────────────────────────────────────────────┐
│                     Internet                                 │
│                         ↓                                   │
│  ┌─────────┐    ┌─────────────┐    ┌──────────────────┐    │
│  │  用户   │───→│ Apache Web  │───→│  PHP 应用服务器   │    │
│  │  浏览器  │    │  服务器     │    │                  │    │
│  └─────────┘    └─────────────┘    └────────┬─────────┘    │
│                                              ↓               │
│                                   ┌──────────────────┐       │
│                                   │     MySQL        │       │
│                                   │   数据库服务器    │       │
│                                   └──────────────────┘       │
└─────────────────────────────────────────────────────────────┘
```

### 问题 1

阅读上述说明和图 5-1，请说明 LAMP 架构中各组件的作用，并分析 Web I/O 性能瓶颈的原因。

**解答**：
- **Linux**：操作系统，提供底层系统调用和资源管理
- **Apache**：Web 服务器，处理 HTTP 请求，管理进程/线程池
- **MySQL**：关系数据库，存储业务数据
- **PHP**：服务器端脚本，生成动态 Web 页面

**I/O 瓶颈原因**：
1. 每个用户请求都需要 Apache 进程处理，频繁的进程创建/销毁开销
2. PHP 动态页面每次都需要查询 MySQL 数据库，大量的磁盘 I/O
3. 数据库连接未池化，每次查询都建立新连接
4. 静态资源（图片/CSS/JS）未有效缓存

### 问题 2

阅读上述说明和表 5-1，请填写 Memcached 应用的空白处 (a)~(e)。

**表 5-1 Memcached 应用配置表**

| 配置项 | 值 |
|-------|-----|

| (b) 缓存策略 | LRU（最近最少使用） |

### 问题 3

阅读上述说明和图 5-2，请说明 MySQL 主从复制的工作原理，以及如何通过主从复制提高系统性能。

**解答**：
- **原理**：主库（Master）将写操作记录到 binlog，从库（Slave）通过 IO 线程读取主库 binlog 并在本地重放（Relay log），SQL 线程执行 SQL 语句
- **提高性能方式**：
  1. 读写分离：写操作走主库，读操作走从库
  2. 负载均衡：多个从库分担读请求
  3. 备份容灾：从库作为主库的实时备份
  4. 故障切换：主库故障时可将从库提升为主库
