# 系统架构设计师核心知识速查

关联：[[个人资料/笔记/软考/系统架构设计师-高级/00_学习总计划|00_学习总计划]] · [[个人资料/笔记/软考/系统架构设计师-高级/01_学习进度看板|01_学习进度看板]] · [[个人资料/笔记/软考/系统架构设计师-高级/02_论文项目底稿|02_论文项目底稿]]

## 一、五大架构风格 ⭐⭐⭐

### 1.1 总览

| 风格大类         | 子风格               | 核心特征           | 典型应用            | 优点           | 缺点          |
| ------------ | ----------------- | -------------- | --------------- | ------------ | ----------- |
| **数据流**      | 批处理序列、管道-过滤器      | 数据从输入到输出的线性变换  | 编译器、ETL、Unix 管道 | 模块独立、可复用、可并发 | 不适于交互强的系统   |
| **调用/返回**    | 主程序/子程序、面向对象、层次结构 | 显式调用，逐层返回      | 传统应用、分层系统       | 逐级抽象、扩展性好    | 层次间耦合高则难改   |
| **独立构件**     | 进程通信、事件驱动(隐式调用)   | 构件独立，通过消息/事件协作 | GUI 框架、微服务、消息队列 | 可扩展、并发好      | 削弱对计算的控制力   |
| **虚拟机**      | 解释器、规则系统          | 提供虚拟执行环境       | JVM、专家系统、DSL    | 高度灵活、自定义规则   | 性能低、只适于特定领域 |
| **仓库(数据中心)** | 数据库、黑板、超文本        | 以共享数据为中心       | IDE、数据库系统、AI 求解 | 数据集中、组件松耦合   | 中心存储成瓶颈     |

### 1.2 高频辨析

| 对比 | 判断标准 |
|------|---------|
| 批处理 vs 管道-过滤器 | 批处理：整体处理完才传递；管道-过滤器：增量传递、逐段处理 |
| 事件驱动 vs 进程通信 | 事件驱动：隐式调用(发布-订阅)；进程通信：显式消息传递 |
| 仓库 vs 黑板 | 仓库：被动共享数据；黑板：主动知识源协同求解(语音识别、信号处理) |

### 1.3 现代架构风格 ⭐⭐⭐

| 风格 | 核心概念 | 关键技术 |
|------|---------|---------|
| **SOA** | 面向服务、服务编排、松耦合 | ESB、WSDL、SOAP、UDDI、服务注册与发现 |
| **微服务** | 单一职责、独立部署、去中心化 | Docker、K8s、API 网关、服务网格、配置中心 |
| **云原生** | 容器化+微服务+DevOps+CI/CD | 服务化、弹性、可观测、韧性、零信任、自动化 |
| **REST** | 资源、统一接口、无状态 | HTTP 方法、URI、JSON、幂等性 |

### 1.4 SOA vs 微服务 ⭐⭐⭐

| 维度 | SOA | 微服务 |
|------|-----|--------|
| 服务粒度 | 粗粒度，功能完整 | 细粒度，单一职责 |
| 通信方式 | ESB 集中式 | 轻量级(API Gateway/直连) |
| 数据管理 | 共享数据库 | 去中心化(每服务一库) |
| 部署 | 整体部署 | 独立部署 |
| 技术栈 | 统一 | 可异构 |
| 治理 | 中心化 | 去中心化 |

### 1.5 ESB 主要功能

1. 应用程序位置透明性
2. 传输协议转换
3. 消息格式转换
4. 消息路由
5. 消息增强
6. 安全支持
7. 监控和管理

## 二、质量属性 ⭐⭐⭐

### 2.1 六大核心质量属性(案例必背)

| 质量属性 | 定义 | 代表参数 | 设计策略 |
|---------|------|---------|---------|
| **性能** | 系统响应能力 | 响应时间、吞吐量 | 优先级队列、增加资源、并发、资源调度、减少开销 |
| **可用性** | 正常运行时间比例 | 故障间隔时间(MTBF) | 心跳、冗余、选举、服务下线、服务监控 |
| **可靠性** | 出错时维持基本功能 | MTTF、MTBF | 心跳、冗余、选举、异常检测 |
| **安全性** | 向合法用户服务+阻止非法用户 | 机密性、完整性、不可否认性 | 认证授权、限制访问、入侵检测、追踪审计 |
| **可修改性** | 快速高性价比变更系统 | 变更代价 | 高内聚低耦合、信息隐藏、多态、接口-实现分离 |
| **可测试性** | 发现故障并隔离定位 | 测试成本 | 专门化接口、关注点分离 |

### 2.2 其他质量属性

| 属性 | 定义 |
|------|------|
| 可变性 | 架构经扩充/变更成为新架构的能力 |
| 互操作性 | 与外部系统交互的能力 |
| 功能性 | 系统完成期望工作的能力 |
| 易用性 | 用户使用难易程度 |
| 可伸缩性 | 数据量增加时维持服务质量 |

### 2.3 开发期 vs 运行期

| 分类 | 属性 |
|------|------|
| **开发期** | 易理解、可扩展、可重用、可测试、可维护、可移植 |
| **运行期** | 性能、安全、可伸缩、互操作、可靠、可用、鲁棒 |

## 三、架构评估 ⭐⭐⭐

### 3.1 四个关键概念(案例必背)

| 概念 | 定义 | 例子 |
|------|------|------|
| **敏感点** | 影响**一种**特定质量属性的构件特性 | "增加缓存层可提升性能" |
| **权衡点** | 影响**多种**质量属性的敏感点 | "提高加密级别→安全性↑但性能↓" |
| **风险点** | 潜在存在问题的架构决策 | "使用未经充分测试的框架" |
| **非风险点** | 可行且可接受的做法 | "使用成熟的关系数据库" |

### 3.2 评估方法对比

| 方法 | 全称 | 核心思想 | 输入 | 输出 |
|------|------|---------|------|------|
| **SAAM** | 软件架构分析方法 | 场景测试，评估可修改性 | 问题描述、需求、架构描述 | 场景评估结果 |
| **ATAM** | 架构权衡分析方法 | 多质量属性评价与折中 | 质量属性场景、架构描述 | 效用树、风险点、权衡点 |

### 3.3 质量属性效用树

```
效用(根)
├── 性能(高)
│   ├── 场景1：1000并发用户下P95≤2s (H,M)
│   └── 场景2：数据量增长10倍后吞吐量不降 (H,H)
├── 可用性(高)
│   └── 场景3：单节点故障后30s内恢复 (H,M)
├── 安全性(中)
│   └── 场景4：外部攻击时1分钟内检测 (M,H)
└── 可修改性(中)
    └── 场景5：新增接口2人天内完成 (M,M)

标注：(重要程度, 实现难度) — H=高 M=中 L=低
```

### 3.4 质量属性场景三要素

- **刺激**：触发系统响应的条件
- **环境**：刺激发生时系统的状态
- **响应**：刺激发生后系统的行为

## 3.5、云架构核心要点 ⭐⭐⭐

> 来自第 1 章 1.1.5 高频考点，常作为早晨第 1 题出现。详见 [[个人资料/笔记/软考/系统架构设计师-高级/知识点/01-绪论#1.1.5 云架构的核心要点（高频考点）|1.1.5 云架构的核心要点（高频考点）]]。

### 主要特点

- **高扩展性**（核心）：通过「数据复制到内存 + 业务封装为处理单元」实现弹性伸缩。

### 四选项辨析（防错表）

| 选项 | 判断 | 本质归类 |
|------|------|---------|
| A. 低成本运维 | ❌ | 衍生优势 |
| B. 高安全性 | ❌ | 取决于具体实现 |
| C. 高扩展性 | ✅ | **主要特点** |
| D. 高可用性 | ❌ | 设计目标 |

### 易混淆架构对比

| 架构 | 核心特征 | 主要特点 |
|------|---------|---------|
| **云架构** | 数据入内存 + 处理单元化 | **高扩展性** |
| **集群架构** | 多机器部署同一应用 | **高可用性** |
| **分布式架构** | 多节点协作完成业务 | **高透明性、高可靠性** |

### 口诀

> **「主要看扩展，运维看优势，安全看实现，可用看目标」**

### 与其他章节的串联

- 第 14 章云原生"弹性"原则：云架构是高扩展性的实现，云原生是云架构 + 微服务 + DevOps 的演进
- 云计算三层模型（IaaS/PaaS/SaaS）：贯穿"高扩展性"主线
- 六大质量属性中的「可伸缩性」：与本题直接对应

## 3.6、UML 三实现类图速查 ⭐⭐⭐

> 来自第 1 章 1.1.2 高频考点，常以"软件体系结构图用什么表示"形式出现。详见 [[个人资料/笔记/软考/系统架构设计师-高级/知识点/01-绪论#1.1.2-quinquies 软件架构的 UML 表示：包图/组件图/部署图 三实现类图辨析|1.1.2-quinquies 软件架构的 UML 表示：包图/组件图/部署图 三实现类图辨析]]。

### 6 要素速查（organizer 标准格式）

| 序号 | 要素 | 内容 |
|------|------|------|
| ① | **一句话定义** | UML 描述"实现"的 3 张图：包图（设计·模块）+ 组件图（实现·构件）+ 部署图（运行·节点） |
| ② | **适用范围** | 面向对象设计/实现阶段描述模块划分、构件组织、硬件部署 |
| ③ | **常见混淆点** | 包图 vs 类图（模块组织 vs 类关系）；组件图 vs 部署图（构件 vs 节点）；MVC/N 层 ≠ UML 图 |
| ④ | **在软考里的考法** | 上午题单选题（"软件体系结构图用什么表示"） |
| ⑤ | **出题陷阱** | 把"物理 = 部署"当两个；把"+1" 误写成类图/组件图/对象图；用 MVC/N 层当 UML 图 |
| ⑥ | **最小可记忆点** | **包图画模块，组件画构件，部署画节点；设计 → 包，实现 → 件，运行 → 部** |

### 三图对照（防错表）

| 图 | 所在阶段 | 4+1 视图归属 | 描述对象 | 核心关系 | 典型提问 |
|----|---------|-------------|---------|---------|---------|
| **包图** | **设计** | 实现视图（逻辑层） | 包（命名空间/模块） | `<<import>>`、`<<access>>`、嵌套 | "软件体系结构图用什么表示" |
| **组件图** | **实现** | 实现视图（物理层） | 构件（可独立部署单元） | `<<provide>>`、`<<require>>` 接口 | "构件/接口依赖图" |
| **部署图** | **运行** | **部署视图** | 节点（服务器/设备） | 节点通信路径、软件到节点映射 | "物理部署拓扑图" |

### 易错辨析（核心）

| 常见错选 | 正确归属 | 字面陷阱点 |
|---------|---------|-----------|
| 软件体系结构图 → 组件图 ❌ | → **包图** ✅ | 中文「组件」「结构」字面相近 |
| 部署图 → 组件图 ❌ | → 组件图只管构件、部署图管节点 | 两者都涉及"物理性"易混 |
| MVC = UML 图 ❌ | MVC 是**架构模式**，不是任何 UML 图 | 「MVC」也是"模型视图控制器"字面迷惑 |

### 易混淆架构/模式 vs UML 图

| 提法 | 真实归属 | 是不是 UML 图 |
|------|---------|--------------|
| **包图 / 组件图 / 部署图 / 类图 / 对象图 / 状态图 / 顺序图 / 活动图 / 用例图 / 通信图** | UML 图 | ✅ |
| **MVC / MVP / MVVM** | 架构模式 / 风格 | ❌ |
| **N 层架构 / 三层架构 / C/S / B/S** | 部署分层模式 | ❌ |
| **微服务 / SOA / 云原生** | 架构风格 | ❌ |
| **SOA / ESB** | 架构风格 | ❌ |

### 关键短语 → 图映射

| 题干关键词 | 锁定图 |
|---|---|
| 「**软件体系结构图**」+「**设计阶段**」+「**模块划分**」 | **包图** ✅ |
| 「**构件**」+「**接口**」+「**`<<provide>>` / `<<require>>`**」 | 组件图 |
| 「**物理节点**」+「**软件到节点映射**」+「**服务器/设备**」 | 部署图 |
| 「**模块组织**」+「**包**」+「**命名空间**」 | 包图 |

### 易错选项速排（4 选 1 类）

| 选项 | 是否 UML 图 | 是否正确 |
|------|-----------|---------|
| A. 模型视图控制器（MVC） | ❌ 架构模式 | 排除 |
| **B. 组件图** | ✅ UML 图 | 实现阶段构件组织 |
| **C. 包图** | ✅ UML 图 | 设计阶段模块组织（**本题正确答案**） |
| D. 2层、3层或N层 | ❌ 部署分层模式 | 排除 |

### 口诀

> **「包图画模块，组件画构件，部署画节点；设计 → 包，实现 → 件，运行 → 部」**

### 与其他章节的串联

## 3.7、软件模式三层金字塔速查 ⭐⭐⭐

> 来自第 1 章 1.1.2 高频考点，常以"基本设计决策 / 最低层模式 / 引用计数"三空形式出现。详见 [[个人资料/笔记/软考/系统架构设计师-高级/知识点/01-绪论#1.1.2-sex 软件模式的层次：架构模式 / 设计模式 / 惯用法|1.1.2-sex 软件模式的层次：架构模式 / 设计模式 / 惯用法]]。

### 6 要素速查（organizer 标准格式）

| 序号 | 要素 | 内容 |
|------|------|------|
| ① | **一句话定义** | 模式按抽象层次分三层——架构模式（顶层·子系统）/ 设计模式（中层·类）/ 惯用法（底层·语言） |
| ② | **适用范围** | 选型时识别模式所属层级；判断"基本设计决策/最低层模式/语言级写法"该填哪层 |
| ③ | **常见混淆点** | 把"模式"按字面等同"设计模式 GoF 23"；分析模式与设计模式混 |
| ④ | **在软考里的考法** | 上午题多空选择（"基本设计决策 / 最低层模式 / 引用计数"） |
| ⑤ | **出题陷阱** | 把引用计数当设计模式；把分析模式当设计模式；三空都选设计模式 |
| ⑥ | **最小可记忆点** | **架构画骨（顶层·子系统），设计画筋（中层·类协作），惯用画皮（底层·语言级）** |

### 三模式金字塔（防错表）

| 层级 | 模式 | 抽象层次 | 典型例子 | 题眼关键词 |
|------|------|---------|---------|-----------|
| **顶层** | **架构模式** | **最高** | 分层、MVC、微服务、事件驱动 | 「**基本设计决策**」「系统骨架」「子系统划分」 |
| **中层** | **设计模式** | **中间** | GoF 23（单例、工厂、观察者……） | 「类与对象协作」「可复用方案」 |
| **底层** | **惯用法** | **最低** | C++ RAII、引用计数、智能指针 | 「**最低层**」「语言级」「引用—计数」 |

### 三空关键词 → 模式速查

| 第 N 空 | 题干措辞 | 锁定 |
|---------|---------|------|
| 第 1 空 | 「开发一个软件系统时的**基本设计决策**」 | **架构模式** ✅ |
| 第 2 空 | 「**最低层**的模式 / 关注设计与实现 / 如何实现构件及构件之间的关系」 | **惯用法** ✅ |
| 第 3 空 | 「**引用—计数**是C++管理动态资源时常用的一种」 | **惯用法** ✅ |

### 易错辨析（设计模式 ≠ 惯用法）

| 常见错选 | 正确归属 | 区分关键 |
|---------|---------|---------|
| 引用计数 → 设计模式 ❌ | → **惯用法** ✅ | 引用计数是 C++ 语言级资源管理写法 |
| MVC → 设计模式 ❌ | → **架构模式** ✅ | MVC 是子系统级骨架 |
| GoF 23 → 架构模式 ❌ | → **设计模式**（中层） ✅ | GoF 是类与对象协作方案 |
| 分析模式 → 设计模式 ❌ | → 分析模式是 OO **分析阶段**，不在三层金字塔内 | 干扰项 |

### 三模式 vs 架构风格辨析

| 概念 | 关注点 | 例子 |
|------|--------|------|
| **架构风格** | 某一**特定应用领域**中系统**组织方式**的**惯用模式**（教程原句） | 物联网层次型、Unix 管道、MVC |
| **架构模式** | 软件系统的**子系统划分**骨架（跨领域通用） | 分层、微服务、事件驱动、SOA |
| **设计模式** | **类与对象**级别的可复用协作方案 | GoF 23 |
| **惯用法** | **特定语言**级别的实现技巧 | C++ RAII、引用计数、智能指针 |

> ⚠️ 架构风格 vs 架构模式：风格带"领域属性"，模式是跨领域骨架；两者都可归到金字塔**顶层**。

### 易错选项速排（4 选 3 类）

| 选项 | 真实归属 | 三空判断 |
|------|---------|---------|
| A. 架构模式 | 顶层 | 第 1 空 ✅ |
| **B. 惯用法** | 底层 | 第 2 空 ✅ / 第 3 空 ✅ |
| C. 设计模式 | 中层 | 三空都不选（除非题干说"类与对象协作"） |
| D. 分析模式 | OO 分析阶段（不在金字塔内） | 三空都不选 |

### 口诀

| 空间 | 别名 | 一句话职责 | 典型产物 |
|------|------|-----------|---------|
| **问题空间**（Problem Space） | 用户/业务视角 | "做什么" | 业务需求、用例、领域概念、业务规则 |
| **解空间**（Solution Space） | 系统视角 | "怎么做" | 架构风格、构件/连接器、接口、部署视图 |
| **跨空间转换** | 需求→架构 | 中间必须有 | **可追踪性（Traceability）** |

### 四个候选选项归类（防错表）

| 选项 | 关注点 | 所属阶段 | 是否"转换过程中" |

| B. 确定架构元素构成 | 架构**识别** | 解空间内部造骨架 | ❌ |

| D. 高层→细粒度架构模型 | 架构**精化** | 同空间内部演化 | ❌ |

| 提法 | 真实归属 | 关注点 | 题面关键词 |
|------|---------|--------|-----------|
| **需求模型 → 架构模型** | **跨空间转换** | **可追踪性**（每个需求项能追溯到架构元素） | 「**需求→架构**」「问题空间→解空间」 |

| B. 架构元素构成 | 识别架构元素 | ❌ 解空间**内部**的事 |
| C. 表格/用例映射 | 保证可追踪性 | ✅ **过程中**的事 |
| D. 高层→细粒度 | 架构精化 | ❌ 同空间**演化**的事（不是跨空间） |

> **「需求→架构问追踪，架构→架构问细化，描述架构问多视图，识别元素问构件」**

## 3.9、4+1 视图标准组成与别名辨析速查 ⭐⭐⭐

> 来自第 1 章 1.1.2-ter 高频考点，常以"典型的 4+1 视图模型包括"形式出现。详见 [[个人资料/笔记/软考/系统架构设计师-高级/知识点/01-绪论#1.1.2-oct 4+1 视图的别名辨析：+1 = 场景 vs 物理 = 部署|1.1.2-oct 4+1 视图的别名辨析：+1 = 场景 vs 物理 = 部署]]。

### 6 要素速查（organizer 标准格式）

| 序号 | 要素 | 内容 |
|------|------|------|
| ① | **一句话定义** | 4 + 1 = **逻辑 + 进程 + 开发 + 物理 +（+1 = 场景 / 用例视图）**——Philippe Kruchten 1995 提出 |
| ② | **适用范围** | 架构描述 / RUP 4+1 视图 / 4+1 角色-视图对应 |
| ③ | **常见混淆点** | **物理视图 = 部署视图**（同义）；+1 = 场景 / 用例视图（两种命名都对） |
| ④ | **在软考里的考法** | 上午题（"典型的 4+1 视图模型包括"） |
| ⑤ | **出题陷阱** | 物理 + 部署并列（同一个视图重命名）；+1 写成类视图/组件视图/对象视图 |
| ⑥ | **最小可记忆点** | **4 加 1：逻辑进开物 + 场景；物理就是部署，+1 是场景或用例** |

### 4+1 视图标准组成（教程原句，必背）

| # | 视图 | 一句话职责 | 常用 UML 图 |
|---|------|-----------|-----------|
| 2 | **进程视图**（Process） | 系统的**并发和同步机制**，关注进程、线程、通信；用于**非功能性需求**（性能、可用性） | — |
| 3 | **开发视图**（Development / 实现） | 软件**模块的组织与管理**，关注开发环境的静态结构 | **包图、组件图** |
| 4 | **物理视图**（Physical） | 软件如何**映射到硬件**，关注部署、拓扑、通信 | 部署图 |
| 5 | **+1 = 场景**（Scenarios）/ 用例视图 | 作为**视图的粘合剂**，描述用例或活动图，展示视图之间的**交互与集成** | 用例图、活动图 |

**关键公式**：
> **4 + 1 = 逻辑 + 进程 + 开发 + 物理 +（+1 = 场景）**

### 核心辨析 1：物理视图 = 部署视图

| 命名体系 | 名称 | 备注 |
|---------|------|------|
| **Kruchten 1995 原版** | **Physical View（物理视图）** | **教程原句采用** |
| **RUP / UML 系统视图** | **Deployment View（部署视图）** | 同义改写 |
| Booch / OOAD 早期 | Physical View | 同上 |

> ⚠️ 两者是**同一个视图的两种叫法**，**不能并列当成两个**。

### 核心辨析 2：+1 = 场景 / 用例视图

| 命名体系 | +1 名称 | 关注什么 |
|---------|---------|---------|
| **Kruchten 1995 原版** | **Scenarios（场景）** | 视图之间的**粘合剂**，描述用例或活动图 |
| **RUP / UML 系统视图** | **Use Case View（用例视图）** | 驱动其他 4 视图的需求核心 |

> ⚠️ 两者都正确；看到「**场景**」或「**用例视图**」都算对；看到「**类视图**」「**组件视图**」「**对象视图**」等其他词当 +1 → 错。

### 典型错选组合速排

| 选项措辞 | 错因 | 是否正确 |
|---------|------|---------|
| 逻辑 + 进程 + 开发 + **物理** + **场景** | 标准 Kruchten 命名 | ✅ **正确答案** |
| 逻辑 + 进程 + 开发 + **物理** + **用例视图** | RUP 改写命名 | ✅ 也对 |
| 逻辑 + 进程 + 开发 + **物理** + **部署视图** | 漏了"+1" | ❌ |
| 逻辑 + 进程 + 开发 + **物理** + **类视图** | "+1" 误用类图（类图是逻辑视图的图） | ❌ |
| **物理视图 + 部署视图** 并列 | 同一视图当成两个，**漏了"+1"** | ❌ |

### 易错选项速排（4 选 1 类）

| 选项 | "+1" 是什么 | 是否正确 |
|------|-----------|---------|
| A. ...部署视图和**场景** | 场景 ✅ 但 4 视图是部署 | ⚠️ "部署"应写"物理" |
| B. ...物理视图和**部署视图** | 部署视图 ❌（不是"+1"） | ❌ 视图数实为 4 |
| **C. ...物理视图和场景** ✅ | 场景 ✅ | ✅ **正确答案** |
| D. ...物理视图和**类视图** | 类视图 ❌（类图是逻辑视图的图） | ❌ |

### 口诀

> **「4 加 1：逻辑进开物 + 场景；物理就是部署，+1 是场景或用例」**

### 与其他章节的串联

- 第 7 章"系统架构设计基础知识"中的**视图（View）vs 视角（Viewpoint）** 区分——视图是结果，视角是约定
- 第 5 章"软件工程基础知识"中的 RUP 4+1 角色-视图对应——同源体系
- 与第 1 章 1.1.2-ter"4+1 视图名称"互为**纵向（视图列表）和横向（别名辨析）** 两条轴
- 与第 1 章 1.1.2-ter-bis"RUP 4+1 视图角色-视图对应"——角色 ↔ 视图对应

## 3.10、架构评审的多视角速查 ⭐⭐⭐

> 来自第 1 章 1.1.2 高频考点，常以"软件架构评审时存在的问题"形式出现。详见 [[个人资料/笔记/软考/系统架构设计师-高级/知识点/01-绪论#1.1.2-novem 架构评审的多视角：4+1 视角的完整性|1.1.2-novem 架构评审的多视角：4+1 视角的完整性]]。

### 6 要素速查（organizer 标准格式）

| 序号 | 要素 | 内容 |
|------|------|------|
| ① | **一句话定义** | 评审架构 = 检查 **4+1 视角完整性**，最常缺失的视角 = **+1（用户视角）** |
| ② | **适用范围** | 架构评审 / ATAM 评估 / 设计审查 |
| ③ | **常见混淆点** | 用错评审视角（用层次型标准评数据流）；把优点当问题（模块独立是数据流优点） |
| ④ | **在软考里的考法** | 上午题（"软件架构评审时存在的问题"） |
| ⑤ | **出题陷阱** | 把"模块独立"当问题；把"没有层次关系"当问题；把"功能交互缺失"当问题 |

### 4+1 视角完整性检查表（评审核心方法）

| 视角 | 关注什么 | 题眼关键词 | 评审时常见缺失 |
|------|---------|----------|--------------|
| **逻辑视图** | 功能/类与对象 | "功能划分""对象关系" | ⚠️ 模块划分不细 |
| **进程视图** | 并发与同步 | "运行时""并发""性能" | ❌ 经常缺失 |
| **开发视图** | 代码组织 | "模块""包""组件图" | ❌ 经常缺失 |
| **物理视图** | 软件到硬件映射 | "部署图""硬件""节点" | ❌ 经常缺失 |
| **+1（场景/用例）** | **用户怎么用** | **"用户""交互""用例"** | ❌ **最常缺失 → 评审高频考点** |

### 典型错答辨析（评审场景必看）

| 错答模式 | 错因 | 修复路径 |
|---------|------|---------|
| 「模块独立是问题」 | 把**优点当问题** | 反问"该特征对该风格而言是优还是劣"——模块独立是数据流优点 |
| 「硬件构件替换不灵活」 | 用**构件架构**标准评数据流 | 数据流是模块替换，不是构件替换 |
| 「没有层次关系是问题」 | 用**层次型**标准评数据流 | 数据流本就不强调层次 |
| 「功能之间交互缺失」 | 没看清图中的箭头 | 数据流图箭头已表达交互 |
| 「没有用户视角」 | **+1 视角缺失** ✅ | 这是评审的高频正确答案 |

### 不同架构风格的评审关注点

| 架构风格 | 评审关注点 | 题眼关键词 |
|---------|----------|----------|
| **数据流** | 用户视角是否缺失 + 数据流是否单向 | "用户""交互""单向" |
| **层次型** | 分层是否清晰 + 每层职责是否单一 | "分层""职责""上下层" |
| **事件系统** | 解耦程度 + 事件总线是否单点故障 | "解耦""总线""故障" |
| **构件架构** | 构件可替换性 + 接口稳定性 | "构件""接口""替换" |

### 评审答题速查表

| 题眼关键词 | 评审问题方向 | 正确答案锁定 |
|----------|------------|------------|
| 「用户」「交互」「用例」 | +1 视角缺失 | C 类（缺用户视角） |
| 「模块独立」 | 评审反问"是优点还是问题" | 锁定"是优点"的反选项 |
| 「硬件构件」 | 用错评审视角（数据流不是构件） | 锁定"用错标准"的反选项 |
| 「层次关系」 | 用错评审视角（数据流不是层次型） | 锁定"用错标准"的反选项 |
| 「功能交互」 | 看图细看箭头（箭头已表达） | 锁定"误判"的反选项 |

### 口诀

> **「评架构，先看 4+1 齐不齐；用户视角（+1）最易缺，看到就锁 C」**
>
> **「数据流看单向，层次型看分层，事件型看解耦——风格不同，评审视角不同」**

## 3.11、虚拟机风格三巨头辨析速查 ⭐⭐⭐

> 来自第 1 章 1.1.2-qua 高频考点，常以"采用哪种架构风格最为合适"形式出现。详见 [[个人资料/笔记/软考/系统架构设计师-高级/知识点/01-绪论#1.1.2-dec 解释器 vs 黑板 vs 规则系统：虚拟机风格三巨头辨析|1.1.2-dec 解释器 vs 黑板 vs 规则系统：虚拟机风格三巨头辨析]]。

### 6 要素速查（organizer 标准格式）

| 序号 | 要素 | 内容 |
|------|------|------|
| ① | **一句话定义** | 虚拟机风格 = **解释器 + 黑板 + 规则系统**——三者核心机制都涉及"间接层"，但应用场景完全不同 |
| ② | **适用范围** | 业务组合/编排 → 解释器；多专家协同求解 → 黑板；规则频繁变化 → 规则系统 |
| ③ | **常见混淆点** | 业务组合 ≠ 多专家协同（解释器 vs 黑板）；业务灵活 ≠ 规则变化（解释器 vs 规则系统） |
| ④ | **在软考里的考法** | 上午题（"采用哪种架构风格最为合适"） |
| ⑤ | **出题陷阱** | 业务组合 → 黑板（张冠李戴）；业务灵活 → 规则系统（混淆概念） |
| ⑥ | **最小可记忆点** | **组合业务用解释器，协同求解用黑板，规则变化用规则；语言 / 数据 / 规则，三虚拟机各自管** |

### 虚拟机风格三巨头对照表（防错表）

| 风格 | 一句话核心 | 核心机制 | 典型应用 | 题眼关键词 |
|------|-----------|---------|---------|----------|
| **解释器** | 解释执行某种"语言" | **解释器引擎 + 被解释的语言 / 脚本** | **BPMN、BPEL、DSL、工作流引擎、服务组合、JVM、Python 解释器** | 「**业务组合 / 编排 / 流程定义**」 |
| **黑板** | 多专家协同求解同一问题 | **多个知识源 + 共享黑板（数据结构）+ 控制** | **语音识别、信号处理、AI 求解、模式识别** | 「**语音识别 / 信号处理 / AI 求解**」 |
| **规则系统** | 基于 if-then 规则推理 | **规则库 + 推理引擎 + 工作内存** | **保险定价、税务计算、信用评分、反欺诈** | 「**规则变化 / 业务规则 / 定价**」 |

### 关键短语 → 风格映射

| 题干关键词 | 锁定风格 |
|-----------|---------|
| 「**业务功能组合 / 编排 / 流程定义**」+「**Web 服务组合**」 | **解释器** ✅ |

```

   └───────────┬─────────────┘
               ↓
   ┌─────────────────────────┐
   │   解释器引擎              │  ← 业务流程引擎 / 工作流引擎
   └───────────┬─────────────┘
               ↓
   ┌─────────────────────────┐
   │   执行：调用 Web 服务    │  ← 服务组合 / 编排
   └─────────────────────────┘
```

## 3.12、数据仓储风格 + IDE 速查 ⭐⭐⭐

| 序号 | 要素 | 内容 |

## 3.13、原型分类四种辨析速查 ⭐⭐⭐

> 来自第 5 章 5.1.7 高频考点，常以"原型的叙述中正确的是"形式出现。详见 [[个人资料/笔记/软考/系统架构设计师-高级/知识点/05-软件工程基础知识|5.1.7 原型分类]]。

### 6 要素速查（organizer 标准格式）

| 序号 | 要素 | 内容 |
|------|------|------|
| ① | **一句话定义** | 原型按**两个维度正交**分四种：水平 vs 垂直（看功能实现）；抛弃 vs 演化（看最终结果） |
| ② | **适用范围** | 需求不清 / 界面验证 / 算法验证 / 迭代开发——4 种场景对应 4 种原型 |
| ③ | **常见混淆点** | 水平 ≠ 算法（水平不实现算法）；演化 ≠ 界面（演化是整个系统）；垂直 ≠ Web（项目类型不在分类标准里） |
| ④ | **在软考里的考法** | 上午题单选题（"原型的叙述中正确的是"） |
| ⑤ | **出题陷阱** | 「水平 + 算法」反向陷阱；「演化 + 界面」双张冠李戴；「垂直 + Web 项目」强行对应 |
| ⑥ | **最小可记忆点** | **水平画界面，垂直验算法；抛弃为需求，演化做产品** |

### 原型分类两个维度对照表

| 维度 | 类型 | 一句话职责 | 一句话类比 | 典型场景 |
|------|------|-----------|-----------|---------|
| **是否实现功能** | **水平原型** | 只模拟界面/交互，**不实现功能** | **橱窗样品**（好看不能用） | 需求澄清、界面验证 |
| **是否实现功能** | **垂直原型** | 对**关键功能**做完整实现 | **试制样机**（核心能用） | 复杂算法验证、技术难点 |
| **最终结果** | **抛弃式原型** | 目的是**获取需求**，用完**抛弃** | **草稿纸**（写了就扔） | 需求不确定/不完整/含糊不清 |
| **最终结果** | **演化式原型** | 原型**迭代演化**为最终系统 | **毛坯房**→精装房 | 迭代开发、需求持续演进 |

### 关键短语 → 原型映射

| 题干关键词 | 锁定原型 |
|-----------|---------|
| 「**需求不确定 / 不完整 / 含糊不清**」 | **抛弃式原型** ✅ |
| 「**界面 / 交互（不实现功能）**」 | **水平原型** |
| 「**关键功能 / 复杂算法**」 | **垂直原型** |
| 「**逐步演化 / 迭代成最终系统**」 | **演化式原型** |

### 易错辨析速查（4 选 1 类）

| 选项 | 关注点 | 是否本题 |
|------|-------|---------|
| A. 水平原型适合算法复杂 | 张冠李戴（水平不实现算法） | ❌ |
| B. 垂直原型适合 Web 项目 | 强行对应（项目类型不在分类标准里） | ❌ |
| **C. 抛弃式原型适合需求不确定** ✅ | 抛弃式的核心目的就是获取需求 | ✅ |
| D. 演化式原型主要用于界面设计 | 双张冠李戴（演化≠界面；界面→水平） | ❌ |

### 口诀

> **「水平画界面，垂直验算法；抛弃为需求，演化做产品」**

## 六、可靠性计算 ⭐⭐⭐

### 6.1 基本公式

| 公式 | 用途 |
|------|------|
| $R(t) = e^{-\lambda t}$ | 可靠度(指数分布) |
| $\text{MTTF} = 1/\lambda$ | 平均无故障时间 |
| $\text{MTBF} = \text{MTTF} + \text{MTTR}$ | 平均故障间隔 |
| $A = \text{MTTF} / (\text{MTTF} + \text{MTTR})$ | 可用性 |

### 6.2 串并联模型

| 结构 | 可靠度公式 | 特点 |
|------|-----------|------|
| **串联** | $R = R_1 \times R_2 \times \cdots \times R_n$ | 全通才通，越串越低 |
| **并联** | $R = 1-(1-R_1)(1-R_2)\cdots(1-R_n)$ | 一通就通，越并越高 |
| **混合** | 先化简再计算 | 串中有并或并中有串 |

## 七、信息安全 ⭐⭐⭐

### 7.1 加密体系

| 类型 | 算法 | 特点 | 用途 |
|------|------|------|------|
| **对称加密** | DES/AES/3DES/IDEA | 速度快、密钥短 | 大量数据加密 |
| **非对称加密** | RSA/ECC/DSA | 速度慢、密钥长 | 密钥交换、数字签名 |
| **摘要算法** | MD5/SHA-1/SHA-256 | 不可逆、固定长度 | 完整性校验 |

### 7.2 数字签名与数字证书

| 概念 | 过程 | 目的 |
|------|------|------|
| **数字签名** | 发送方用**私钥**加密摘要 → 接收方用**公钥**验证 | 不可否认性+完整性 |
| **数字证书** | CA 签发，将公钥与身份绑定 | 公钥合法性认证 |
| **数字信封** | 用接收方公钥加密对称密钥 | 安全传输密钥 |

### 7.3 安全模型

| 模型 | 关注点 | 核心策略 |
|------|--------|---------|
| BLP(Bell-LaPadula) | 机密性 | 不上读不下写(高→低) |
| Biba | 完整性 | 不下读不上写(低→高) |
| Clark-Wilson | 完整性 | 受控转换+职责分离 |
| 零信任 | 全面安全 | 永不信任，始终验证 |

1. **条理清晰**：分点作答，编号标注
2. **宁多勿少**：正向给分，看到对的给分，错的不扣分
3. **绝不留空**：不会的也写上相关理解
4. **用词精确**：使用教材术语，不要口语化
5. **合理选题**：选自己最有把握的两道

## 十、设计原则(SOLID+) ⭐⭐

| 原则 | 要点 | 口诀 |
|------|------|------|
| **S** 单一职责 | 一个类只有一个变化原因 | 一职一责 |
| **O** 开闭 | 对扩展开放，对修改封闭 | 加不加改 |
| **L** 里氏替换 | 子类可替换父类 | 子类替父 |
| **I** 接口隔离 | 多个专门接口优于一个胖接口 | 接口要瘦 |
| **D** 依赖倒置 | 依赖抽象而非具体实现 | 依赖抽象 |
| 组合重用 | 优先用组合而非继承 | 组合优于继承 |
| 迪米特 | 最少知识原则 | 少知道少耦合 |

## 十一、项目管理计算 ⭐⭐

| 公式 | 用途 |
|------|------|
| 盈亏平衡点 = 固定成本 ÷ (单价 - 单位变动成本) | 项目可行性分析 |
| 关键路径 = 最长路径 | 项目最短工期 |
| 总浮动 = 最迟开始 - 最早开始 | 非关键活动可延迟时间 |
| $E = (O + 4M + P) / 6$ | PERT 三点估算 |

## 十二、REST 五原则 ⭐⭐

1. 网络上的所有事物都被抽象为**资源**
2. 每个资源对应唯一的**资源标识**(URI)
3. 通过**通用连接件接口**对资源进行操作(HTTP 方法)
4. 对资源的操作**不会改变资源标识**
5. 所有操作都是**无状态**的
