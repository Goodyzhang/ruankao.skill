# 系统分析与设计：第 243～279 题整理

## 第 243～245 题：采购系统数据流图

### 材料摘要与原图

业务覆盖库存预警、采购下单、到货核对、质量检查和库存更新。读图时分别追踪订购、验收、入库以及异常通知；外部角色由其输入和接收的信息辨认。

### 第 243 题／问题 1：辨认外部实体（10 分）

**要求摘要**：结合业务说明，为 E1～E5 命名。

**网站答案整理**：E1＝供应商；E2＝采购部门；E3＝检验员；E4＝库管员；E5＝S/R 职员。

**解题过程**：先从辨识度最高的数据流入手。E1 提交提单且接收采购订单，对应供应商；E2 发检查和采购请求并接收低库存信息，对应采购部门。E3 接收验证后的提单并报告缺陷，对应检验员。E4 接收可入库部件清单并提供采购数量，对应库管员。E5 接收提单并反馈装运差错，对应运输接收职员。每个角色至少用一条输入和一条输出交叉核对，避免仅凭名称猜测。

**方法边界**：DFD 的“外部”相对于软件系统边界；公司内部员工也可以是外部实体。不要把业务部门误认成内部加工。

### 第 244 题／问题 2：辨认数据存储（8 分）

**要求摘要**：为 D1～D4 命名。

**网站答案整理**：D1＝库存表；D2＝采购订单表；D3＝质量标准表；D4＝供应商表。

**解题过程**：根据存储与加工之间的读写语义判断。D1 提供库存信息并接收数量更新，保存库存状态；D2 接收新订单、向核验环节提供订单并接收完成标记，保存采购订单；D3 向质量检查提供标准；D4 向下单加工提供供应商资料。答案使用说明中的业务名称，不自行细化为数据库物理表结构。

**易错点**：数据流是一次传递的信息，数据存储是供后续读取的持久信息集合。“供应商信息”是流的名字，“供应商表”是存储名字。

### 第 245 题／问题 3：补充缺失数据流（7 分）

**要求摘要**：列出遗漏的数据流名称、起点、终点。

**网站答案整理**：

| 数据流 | 起点 | 终点 |
|---|---|---|
| 原有部件库存量 | D1 | P5 |
| 产品送检 | P3 | P4 |
| 装运错误通知 | P3 | E1 |
| 缺陷装运通知 | P4 | E1 |

**解题过程**：

1. 先查父子图平衡。顶层系统会向供应商发送通知，分解后应能找到具体负责通知的加工。到货不符由 P3 产生，质量不合格由 P4 产生，因此分别补到 E1。
2. 再查业务衔接。P3 核验通过后要将送检信息交给 P4。若图中没有这条边，P4 就缺少检验对象的信息来源。
3. 最后查计算输入。P5 要完成库存累加，需要“旧库存＋本次数量”；本次数量已由 E4 提供，但旧库存还须由 D1 读取。P5→D1 的写入边无法代替 D1→P5 的读取边，两条边方向和用途不同。

**术语说明**：网站将 P3→P4 命名为“产品送检”。DFD 表示信息流，应理解为与送检部件相关的已验证提单及部件项目信息，不能把实物运输线直接当成数据流。网站答案称 P4“校验部件质量”，用户原图写“检验部件质量”，两者均指图中的 P4。

**完整性记录**：页面题干称“问题 1 至问题 4”，实际第 243～245 题展示问题 1～3，分值为 10＋8＋7＝25；第 246 题已是商业情报案例。未见第四问，不据此补写。

## 第 246 题起：商业情报系统

### 第 246 题／问题 1：流程图与数据流图（5 分）

**要求摘要**：300 字以内说明两类图的含义、区别，以及分析阶段采用 DFD 的理由。

**网站答案要点**：DFD 描述业务功能边界与数据传递；流程图刻画处理的控制顺序。网站还从并行、计时和逻辑／物理建模角度作对照。

**可用于答题的自主表述**：数据流图描述系统边界、数据来源去向及各加工对数据的转换，用于建立功能逻辑模型；流程图描述步骤、判断、循环等控制关系。DFD 中的箭头说明传递什么数据，不规定统一的执行时序；流程图的箭头用于表达控制如何推进。本案例需要明确情报处理功能和外部角色间的数据联系，当前处于系统分析阶段，因此采用 DFD 更贴合任务。

**分析方法**：把题干目标拆成“业务功能、系统边界、数据联系”三个判别点，与 DFD 对应；不要只写“因为处于分析阶段”。先给定义，再比较箭头含义，最后回到案例说明选择理由。

**理解边界**：DFD 不规定调度时序，不意味着实现时所有加工必然并行。流程图也不必然等同于某一种物理实现。网站的对照表适合识别本题考查口径，复习时应抓住数据关系与控制关系的核心区别。

### 第 247 题／问题 2：识别错误并归并为 0 层图（5 分）

**要求摘要**：找出 1 层 DFD 的错误及原因，并抽象出子系统 0 层图。

**网站答案整理与原图核验**：分类训练加工仅有输入、没有输出，形成黑洞；分类处理加工仅有输出、没有输入，形成奇迹。规则文件直接从数据汇集系统写入规则库，缺少加工；配置信息直接从用户传到数据汇集系统，没有经过所建模子系统的加工。

**解题过程**：先逐个加工清点入边、出边，再逐条检查端点类型。本图分类处理到规则库的“分类规则”箭头朝向规则库，因此它是加工的输出，不能误读成读取规则的输入。随后检查外部实体之间、外部实体与存储之间是否存在直接连线。错误要写出具体对象和原因，仅写“图不平衡”没有定位。

**0 层图应表达的关系**：将内部加工与规则库存储隐藏，保留一个“情报分类子系统”加工；数据汇集系统向它提供样本数据、规则文件；用户向它提供配置信息；它向用户输出分类结果。这与页面答案图的四条边一致。

**抽象方法**：先围出子系统边界，记录所有跨边界信息，再合并内部结构。原图本身存在错误，不能机械地把错误连线原封不动提升到上层；应结合纠错后的逻辑确定信息由子系统接收或输出。

### 第 248 题／问题 3：高质量 DFD 的原则（5 分）

**要求摘要**：300 字以内说明三个设计原则。

**网站答案整理**：复杂性最小化、接口最小化、数据流一致性。

**可用于答题的自主表述**：通过逐层分解把复杂系统划分为便于理解的功能单元，每层保持适当粒度；在满足需求的前提下减少加工之间不必要的连接，降低相互依赖；保证父加工与子图的边界输入输出内容一致，并使每个加工的输入足以解释输出，避免只有输入或只有输出的加工。

**分析方法**：分别回答“单张图是否容易理解”“元素之间是否连接过多”“数据能否从来源追踪到结果”。接口最小化不允许删掉业务必需的流；父子平衡比较数据内容，允许有明确定义的组合与分解，不能仅按箭头条数判断。

**完整性记录**：第 246～248 题共三个小问，5＋5＋5＝15 分；第 249 题进入新的在线教育案例。

## 第 249 题起：在线教育平台

### 材料摘要

平台同时面向学生与教师，覆盖教学活动及其管理，要求承受并发访问并保障业务数据。后续问题围绕后端框架、负载分配和相关 Web 技术展开。

### 第 249 题／问题 1：后端框架对比（8 分）

**要求摘要**：从开发效率、性能、安全和规模四个维度填补 Spring Boot 与 Django 对比表。

**网站填空口径（摘要）**：① Spring Boot 通过自动配置及依赖管理简化开发；②题库将 Django 的相对性能评为较弱；③题库认为 Spring Boot 要另行实现防护或依靠 WAF；④题库将 Django 定位于较小站点，对大型分布式应用作负面评价。

**解题方法**：每个空先定位“行维度＋列框架”，再填写同一层次的能力描述。开发效率写减少哪些配置或重复工作；性能写题库比较口径；安全写机制；规模写场景。不要把编程语言、架构模式或部署产品填入能力空格。

**证据边界**：以上是当前网页显示的参考答案，未据此做现代版本的技术选型验证。实际工程中，性能受负载、I/O、数据库与部署方式影响；安全应检查具体配置和组件能力；是否适合大规模系统也取决于架构和团队。不能单凭此表得出“某框架只能开发小系统”的结论。

### 第 250 题／问题 2：负载均衡技术及取舍（10 分）

**要求摘要**：300 字以内列出负载均衡技术，说明优点和缺点。

**网站答案要点**：重定向、DNS、NAT、反向代理、混合型五类；分别涉及客户端参与、DNS 更新延迟、转发节点瓶颈、代理适配和组合管理复杂度。

**可用于答题的自主表述**：重定向由客户端转向目标服务器，转发压力小，但增加交互并需避免循环；DNS 分流部署简便，缓存使故障切换不够及时；NAT 对应用透明，但进出流量汇聚可能限制吞吐；反向代理可按请求特征分配流量并结合缓存，但代理本身有资源开销和可用性要求；混合方案可分层兼顾地域与实例调度，代价是配置、监控及故障定位更复杂。

**分析方法**：沿一次请求的路径回答“谁作分配决定、流量是否经过它、它如何知道目标可用”。据此推导性能开销和切换局限。不要只列轮询、加权、最少连接等算法，因为本题按实现技术分类。考试高峰需要同时考虑分流能力与均衡器自身故障，增加后端实例并不能自动消除入口单点。

### 第 251 题／问题 3：中间件类型与产品（7 分）

**要求摘要**：列出可用于教育平台的中间件并给出具体产品，网页注明答出七类即可。

**网站答案产品映射及应用分析**：

| 类型 | 页面给出的产品示例 | 本案例如何联系用途 |
|---|---|---|
| Web 服务 | Nginx、Apache | 承接 Web 请求或静态资源 |
| 缓存 | Redis、Memcached | 缓存热点课程信息，减少重复读取 |
| 消息队列 | RabbitMQ、Kafka | 将非即时处理任务与请求解耦 |
| API 网关 | Tyk | 统一管理 API 入口 |
| 数据访问连接管理 | HikariCP | 复用数据库连接 |
| 分布式事务 | Seata | 处理适用场景下的跨服务事务协调 |
| 负载均衡 | Nginx、HAProxy | 把访问分配到服务实例 |
| 监控及展示 | Prometheus、Grafana | 观察指标与服务运行状态 |

**解题方法**：按“类型—产品—用途”成组回答，优先选择七种不同职责。Nginx 出现在两类中可以解释其不同用途，但不应仅靠重复产品名凑数量。缓存不能替代成绩数据的可靠存储，消息异步处理也要符合考试提交的确认语义。

**完整性记录**：第 249～251 题三问分值为 8＋10＋7＝25 分，均已读取网站答案。

## 第 255 题：教学管理系统 UML（三问合页）

### 材料与问题摘要

系统面向管理员、教师和学生，管理教学资料、开课与选课、考试及补考，并在月末通过打印机输出考勤。所有业务功能要求用户已登录。本页一次展示三个小问，分别考查参与者、用例关系、类关系，分值为 7、7、11 分。

### 问题 1：参与者

**网站答案整理**：学生、教师、管理员、时间、打印机。

**解题分析**：先找操作系统的人，再找与系统交换信息的设备及外部触发源。打印机接收考勤输出；“每月月底”提供定时触发。考试口径将时间列作参与者，工程建模可具体表现为外部时钟或调度角色。学校、系、课程是被管理的业务对象，不能因出现在需求名词中就全部列为参与者。

### 问题 2：用例关系

**网站答案整理**：页面列包含、扩展；注册课程与登录按包含处理，考试与补考按扩展处理。

**解题分析**：按本题预期，注册课程包含登录行为，include 箭头由“注册课程”指向“登录系统”。补考仅在不及格条件下发生，extend 箭头由“参加补考”指向“参加考试”。答关系时最好写明方向和触发条件。

**知识补全**：UML 用例之间还可以有泛化关系，网页的总类目列举不完整。另应区分“已经登录”这一前置条件与“每次注册课程都执行登录”这一被包含行为；单凭前置条件不能机械断定 include。本题采用网站给定的建模口径，迁移时回到行为是否必然发生。

### 问题 3：类关系

**网站答案整理**：列举关联、聚合、组合、依赖、泛化；University–Student 为聚合，University–Department 为组合，Student–Course 为关联。

**解题分析**：学校与学生按可独立存在的整体／部分关系理解，采用聚合；学校与系按组成单位理解，题库采用组合；学生选修课程体现关联。聚合与组合的菱形均画在整体端，即 University 一端，组合使用实心菱形。泛化空心三角指向父类；依赖表示使用关系，不能仅因两个对象有联系就选依赖。

**边界**：组合需要整体对部分具有强所有权等语义，具体生命周期须由模型约束确定，不是看到组织上下级就一律组合。更完整的 UML 分类还包括实现；这里保留题库所列项目并说明其范围。

## 第 256～259 题：在线会议审稿系统 ORS

### 材料摘要与术语表截图

作者注册后提交稿件并查询审阅结果；审稿人设置研究兴趣、评阅和查看录用情况；主席继承审稿人职责，并负责查看、分配稿件及结束评审。提交过程依次收集标题摘要、主题、文件位置，未完成则重做，完成后上传并通知。

### 第 256 题／问题 1：参与者编号（8 分）

**要求摘要**：按英文名称表填写 A1～A4。

**网站答案整理**：A1＝User，A2＝Author，A3＝Reviewer，A4＝PCChair。

**解题链**：作者与审稿人都是用户，主席是特殊审稿人。先构造这两层“是一种”关系，再结合图中角色对应的功能核验。主席继承 Reviewer 能力，无需重复连接所有通用用例。泛化箭头从特殊角色指向一般角色。

### 第 257 题／问题 2：用例编号（6 分）

**要求摘要**：填写 U1～U3 的英文用例名称。

**网站答案整理**：U1＝list accepted/rejected papers；U2＝browse submitted papers；U3＝assign paper to reviewer。U2 与 U3 可互换。

**解题链**：先把 Reviewer 已有能力从需求中逐项对齐，缺少的查看录用结果即 U1；主席独有的浏览投稿与分配稿件占据 U2、U3。由于两个空在约束上对称，网页允许互换。答题应完整写出动作与对象，不只写 browse 或 assign。

### 第 258 题／问题 3：用例关系（4 分）

**要求摘要**：填写图中两条用例关系。

**网站答案整理**：（1）extend；（2）include。

**解题链**：依题库图示，尚未登录时执行登录作为提交过程的条件扩展；关闭评审明确要求列出录用／拒绝的稿件，因此包含该列表用例。extend 箭头从扩展行为指向被扩展的基础用例；include 从调用用例指向被包含用例。判断顺序为“是否必做→是否仅在条件满足时发生→箭头方向”。不能用“先做、后做”的时间顺序代替关系语义。

### 第 259 题／问题 4：活动步骤（8 分）

**要求摘要**：填写 Action1～Action4，使用名称表中的英文。

## 第 272 题：在线销售系统设计模式

### 材料与问题摘要

促销计算复杂且经常变化，希望新增促销时少改控制器；税率调用来自不同供应商，方法接口不同，希望更换供应商时少改系统。三问依次考模式类别作用、给定九个模式分类和两类需求的解决方案。

### 问题 1、2：模式作用及分类

**网站答案整理**：创建型控制对象实例化，题中包含 Builder、Prototype；结构型组织类和对象，题中包含 Adapter、Facade、Proxy；行为型组织交互和职责，题中包含 Command、Mediator、State、Strategy。

**分析方法**：按意图分类而非实现语法。使用继承不代表结构型，拥有工厂方法也不代表整个模式是创建型。Builder 分离复杂对象的构造步骤，Prototype 通过原型复制创建对象；Adapter 转换接口、Facade 提供统一入口、Proxy 控制访问；其余四种分别组织请求、协调交互、状态行为和算法替换。

### 问题 3：策略与适配器

**网站答案要点**：促销采用 Strategy；供应商接口采用 Adapter。

**方案一**：定义统一促销计算接口，将百分比折扣、现金减免等各自封装为策略。控制器委托当前策略计算，选择逻辑依据订单条件配置。新增促销主要增加策略实现，原控制器调用接口保持稳定。核心证据是“多种可替换计算＋算法经常变”，不能只因系统有会员状态就选 State。

**方案二**：定义系统自己的税率计算接口，每个供应商适配器持有对应 SDK／类，把统一调用转换为该供应商的方法与参数。业务逻辑依赖稳定接口，更换供应商替换或新增适配器。接口不兼容是关键；Facade 侧重简化子系统入口，Proxy 侧重访问控制，均不能直接替代接口转换。

**迁移提示**：先找变化点，再说封装在哪里、调用方依赖什么、变化时修改哪些类。模式名称必须配合这条责任分配链。

### 问题 3：OMT 三模型及联系

**网站答案要点与自主整合**：对象模型描述对象、属性、操作与静态关系；动态模型描述事件触发下的状态变化及合法顺序；功能模型描述输入到输出的值变换。对象模型提供承载行为和数据的结构，动态模型说明何时触发操作，功能模型说明操作计算什么，三者共同约束一个系统，均可服务需求分析。

**方法边界**：题目按 OMT 语境时，功能模型常用 DFD；不要把它与另一套 UML 用例驱动分析口径混写。以预约为例，患者、医生、预约记录属于结构，待确认／已预约／已取消体现状态，输入选择并得到预约结果体现功能转换。
