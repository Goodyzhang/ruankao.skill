## 1. V 模型：测试与开发阶段的对应

[考点] 上午选择题 | [高频]

```
需求分析 ←—————— 验收测试
    ↓                   ↑
概要设计 ←—————— 系统测试
    ↓                   ↑
详细设计 ←—————— 集成测试
    ↓                   ↑
   编码    ←—————— 单元测试
```

| 开发阶段 | 对应的测试 | 谁来测 |
|---------|-----------|--------|
| 需求分析 | **验收测试** | 用户/客户 |
| 概要设计 | **系统测试** | 测试团队 |
| 详细设计 | **集成测试** | 测试团队 |
| 编码实现 | **单元测试** | 开发人员 |

> **记忆**：V 字左半边从上到下是开发，右半边从下到上是测试，水平对应。

## 4. McCabe 复杂度

[考点] 上午选择题+计算 | [高频]

### 三种等价计算方法

$$V(G) = m - n + 2$$
- m = 边的数量
- n = 节点的数量

$$V(G) = P + 1$$
- P = 判定节点（二分支）的数量
- 判定节点：if、while、for、case 中的条件判断

$$V(G) = R$$
- R = 封闭区域数（包括最外部的区域）

### 示例
```
    ○→○→○→○
      ↓   ↑
      ○→○→○
```
边 m = 9，节点 n = 7 → V(G) = 9 - 7 + 2 = **4**
（即需要 4 个测试用例覆盖所有路径）
判定节点（两个菱形）P = 3 → V(G) = 3 + 1 = **4** ✅

## 5. 软件系统工具分类

[考点] 上午选择题 | [必背]

### 划分维度：按软件过程活动

```
软件系统工具
├── 软件开发工具           → 解决"做出来"
│需求分析 / 设计 / 编码与排错
│
├── 软件维护工具           → 解决"改旧版本"
│版本控制 / 文档分析 / 开发信息库 / 逆向工程 / 再工程
│
└── 软件管理和软件支持工具  → 解决"管过程"
项目管理 / 配置管理 / 软件评价 ⭐
```

### 三类工具速查表

| 大类 | 包含工具 | 关键词联想 |
|------|---------|-----------|
| **软件开发工具** | 需求分析、设计、**编码与排错** | "做出来"——生命周期前段 |
| **软件维护工具** | 版本控制、文档分析、开发信息库、**逆向工程**、**再工程** | "改旧版"——已交付后的改造 |
| **软件管理和软件支持工具** | 项目管理、配置管理、**软件评价** | "管过程"——元视角 |

### 三步判断法
1. **看工具名字关键词** → 评价/项目/配置 → 管
2. **看工具管哪一阶段** → 做/改/管
3. **入座 3 类**

| 工具名关键词 | 联想类别 |
|------------|---------|
| 需求、设计、编码、排错 | 软件**开发**工具 |
| 版本、文档、信息库、逆向、再工程 | 软件**维护**工具 |
| **项目、配置、评价** | 软件**管理和支持**工具 |

### 易错陷阱
- ❌ **"评价" ≠ "排错"**：评价是 management 视角的**度量**（复杂度、合规性），不是开发视角的除虫
- ❌ **"逆向工程"是维护不是开发**：分析已有产品 → 改造/理解 → 归维护
- ❌ **"信息库"是维护不是管理**：开发信息库（Repository）保存版本/工件 → 归维护

### 一句话口诀

> **开发做、维护改、管理评**—— 评价找管理，逆向/版本找维护，编码/设计找开发。

## 6. 信息系统建模方法 —— 三剑客

[考点] 上午选择题 | [必背]

### 母规则：视角决定方法，方法决定工具

| 建模方法 | **视角** | **基本工具** | 图元素 |
|---------|---------|------------|--------|
| **结构化建模方法** | **过程为中心** | **数据流图（DFD）** | 加工 / 数据流 / 数据存储 / 外部实体 |
| **信息建模方法** | **数据为中心** | **实体联系图（ERD）** | 实体（矩形）/ 属性（椭圆）/ 联系（菱形） |
| **面向对象建模方法** | **对象为中心** | 用例图 / 类图 / 顺序图等 | 对象 / 类 / 用例 |

### 三步判断法
1. **看题干第一句关键词** —— "**过程**为中心 → DFD"；"**数据**为中心 → ERD"；"**对象**为中心 → UML"
2. **看题目问什么** —— 是问"基本工具"还是"特征"
3. **入座三剑客**

### 易错陷阱
- ❌ **"信息建模" ≠ "结构化建模"**：前者数据视角（ERD），后者过程视角（DFD）。题**第一句**就是母规则
- ❌ **"数据流图"管"过程"不管"数据"**：名字带"数据"二字，但描述的是数据怎么**流过加工**——过程视角
- ❌ **"数据字典"** 不是建模工具，是**辅助文档**，列出数据项定义/类型/含义
- ❌ **"流程图"** 是程序/算法描述工具，**不是系统建模工具**

### ERD 图元素速查

| 元素 | 图形 | 含义 |
|------|------|------|
| **实体** | 矩形 | 现实世界中可区分的对象（如"学生"） |
| **属性** | 椭圆 | 实体的特征（如"学号、姓名"） |
| **联系** | 菱形 | 实体间的关系（如"选课"） |

### 一句话口诀

> **过程找 DFD，数据找 ERD，对象找 UML** ——看到"数据/数据"为中心 → ERD，看到"过程/功能"为中心 → DFD。

## 7. 需求分类（业务 / 用户 / 系统 + 功能 / 非功能 / 设计约束）

[考点] 上午选择题 | [高频]

需求分三层：

- **业务需求**：反映组织 / 客户对系统的高层次目标，回答"为什么做"。
- **用户需求**：用户使用系统完成什么任务，从用户视角描述。
- **系统需求**：从开发者视角对系统的具体要求，包含三类细分：

| 子类 | 关注点 | 典型问句 |
|------|--------|----------|
| **功能需求** | 系统应提供的具体行为 | "系统做什么？" |
| **非功能需求** | 性能、可靠性、安全、易用、可维护等质量属性 | "做到什么程度？" |
| **设计约束** | 限制实现技术的硬性条件（平台、语言、数据库、协议、法规） | "必须用什么做？" |

### 7.1 判别规则（动作 / 质量 / 限制）

| 题干特征 | 归类 |
|---------|------|
| 描述**具体业务动作**（录入、计算、生成、提交） | 功能需求 |
| 描述**质量属性**（响应时间、密码策略、可用率、易学性） | 非功能需求 |
| 指定**实现技术**（国产库、特定语言、特定平台、合规标准） | 设计约束 |

### 7.2 易错点

- 把"密码 30 天改 + 不能重用最近 5 次"（安全质量）读成"系统要做的具体行为" → 误判为功能需求，正确为**非功能需求**。
- 把"使用国产数据库"读成"性能 / 安全需求"，正确为**设计约束**。
- 业务需求和系统需求不要混用：业务需求回答"为什么"，系统需求回答"做什么 / 做到什么程度 / 用什么做"。
